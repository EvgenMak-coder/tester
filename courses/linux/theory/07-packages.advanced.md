# Подписи репозиториев

`apt` доверяет репозиторию не потому, что соединение зашифровано, а потому, что список пакетов в нём подписан ключом владельца. Открытая часть этого ключа должна лежать в системе. Если её нет, `apt update` отвечает так:

```
W: GPG error: https://repo.example.com stable InRelease:
The following signatures couldn't be verified because the public key is not available: NO_PUBKEY 7EA0A9C3F273FCD8
```

Пакеты из такого репозитория ставиться не будут. Порядок подключения стороннего репозитория состоит из двух шагов:

1. Скачать ключ разработчика и положить его в `/etc/apt/keyrings/`.
2. В описании репозитория указать этот ключ параметром `signed-by`.

```
deb [signed-by=/etc/apt/keyrings/example.gpg] https://repo.example.com stable main
```

Параметр `signed-by` привязывает ключ к одному репозиторию. Старый способ — добавить ключ в общее хранилище командой `apt-key` — давал ему власть над всеми репозиториями сразу и потому объявлен устаревшим.

# Прерванная установка

`dpkg` ставит пакет в два приёма: сначала распаковывает файлы, потом запускает сценарии настройки. Если процесс оборвался между ними — выключили питание, закрыли терминал, — пакеты остаются распакованными, но ненастроенными:

```
E: dpkg was interrupted, you must manually run 'sudo dpkg --configure -a' to correct the problem.
```

Сообщение само называет лекарство. Команда `dpkg --configure -a` доводит настройку до конца для всего, что осталось. Если после неё остались неудовлетворённые зависимости, помогает `sudo apt --fix-broken install`.

Чего делать нельзя — удалять каталог `/var/lib/dpkg`. В нём лежит база установленных пакетов, без неё система забудет обо всём, что в ней стоит.

# Блокировка

Две программы не могут менять базу пакетов одновременно. Первая ставит блокировку, вторая получает отказ:

```
E: Could not get lock /var/lib/dpkg/lock-frontend. It is held by process 1423 (unattended-upgr)
```

В сообщении указан процесс, который держит блокировку. Чаще всего это служба автоматических обновлений, которая просыпается вскоре после загрузки. Правильное действие — подождать: блокировка снимется сама.

Удалять файл блокировки или убивать процесс через `kill -9` опасно: установка оборвётся посередине, и получится ситуация из предыдущего раздела, только хуже.

# Какая версия будет установлена

Когда один пакет есть в нескольких репозиториях, `apt` выбирает по приоритетам. Что именно он выберет, показывает `apt policy`:

```
apt policy nginx
```

В выводе три вещи: установленная версия, версия-кандидат и таблица всех доступных версий с приоритетом и репозиторием каждой. Приоритеты меняют в каталоге `/etc/apt/preferences.d/` — так закрепляют пакет за определённым репозиторием.

# Конкретная версия и откат

Версию указывают через знак равенства:

```
sudo apt install nginx=1.24.0-1
```

Так же понижают версию после неудачного обновления: называют старую, и `apt` её вернёт, если она ещё есть в репозитории. Запись через двоеточие означает другое — архитектуру: `nginx:arm64`.

У `dnf` для отката есть удобнее средство — журнал транзакций:

```
dnf history
sudo dnf history undo last
```

`history` показывает список операций, `undo` отменяет выбранную целиком, возвращая прежние версии всех затронутых пакетов.

# Сборка из исходников

Программу, которой нет в репозиториях, собирают сами. Классическая последовательность:

```
./configure
make
sudo make install
```

`configure` проверяет систему и готовит сборку, `make` компилирует, `make install` раскладывает файлы.

По умолчанию всё устанавливается в `/usr/local`. Это не случайность: каталог `/usr` принадлежит менеджеру пакетов, и ручная установка туда может быть затёрта следующим обновлением. `/usr/local` отведён под то, что администратор ставит сам. Другое место задаёт `./configure --prefix=/opt/app`.

О собранной так программе менеджер пакетов не знает: он её не обновит и не удалит. Следить за исправлениями безопасности придётся самому, поэтому сборка из исходников — крайний вариант.

# Разделяемые библиотеки

Программа редко самодостаточна: при запуске системный загрузчик подгружает библиотеки, от которых она зависит. Если какой-то нет, запуск не удастся:

```
./report: error while loading shared libraries: libpq.so.5: cannot open shared object file
```

Все нужные библиотеки и то, найдены ли они, показывает `ldd`:

```
ldd ./report
```

Напротив отсутствующих стоит `not found`. Дальше ищут пакет, в котором лежит библиотека, и ставят его.

Загрузчик ищет библиотеки в стандартных каталогах и по кэшу. Если библиотека установлена в необычное место, каталог добавляют в `/etc/ld.so.conf.d/` и обновляют кэш:

```
sudo ldconfig
```

# Проверка целостности

Менеджер пакетов помнит, какими файлы были при установке. Это позволяет проверить, не изменил ли их кто-то.

```
rpm -V openssh-server
sudo dpkg --verify openssh-server
```

Команда сверяет размер, контрольную сумму, права и владельца каждого файла с базой и печатает расхождения. Пустой вывод означает, что всё совпало.

Изменённые файлы настроек в выводе — норма, их правят намеренно. Изменённый исполняемый файл — повод для расследования.

# apt или apt-get

В сценариях автоматизации вместо `apt` пишут `apt-get` и `apt-cache`. Программа `apt` рассчитана на человека: у неё индикатор выполнения, цвет, и её вывод может меняться от версии к версии. При запуске не в терминале она сама об этом предупреждает. У `apt-get` интерфейс стабильный, на него можно полагаться в скриптах.

Для полностью автоматической установки добавляют ключ `-y` и переменную, которая отключает вопросы:

```
sudo DEBIAN_FRONTEND=noninteractive apt-get install -y nginx
```

# Коротко

- `NO_PUBKEY` — нет ключа репозитория; его кладут в `/etc/apt/keyrings` и указывают через `signed-by`.
- После оборванной установки — `sudo dpkg --configure -a`.
- При занятой блокировке ждут, а не удаляют файл.
- `apt policy пакет` показывает версии, приоритеты и кандидата.
- Конкретная версия: `apt install пакет=версия`; откат в RHEL: `dnf history undo`.
- Собранное из исходников попадает в `/usr/local` и не обновляется менеджером.
- `ldd` показывает недостающие библиотеки, `ldconfig` обновляет кэш загрузчика.
- `rpm -V` и `dpkg --verify` сверяют файлы с базой пакетов.
- В скриптах — `apt-get`, а не `apt`.
