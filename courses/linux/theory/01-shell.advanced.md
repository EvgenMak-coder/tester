# Что оболочка делает со строкой

Между нажатием Enter и запуском программы строка проходит несколько преобразований, всегда в одном порядке. Большинство неожиданностей в командной строке объясняется этим порядком.

1. **Фигурные скобки** порождают строки: `file{1..3}.txt` превращается в три слова.
2. **Подстановки**: переменные `$name`, команды `$(…)`, арифметика `$((…))`.
3. **Разбиение на слова**: результат подстановок без кавычек режется по пробелам.
4. **Шаблоны имён**: слова со знаками `*`, `?` и `[…]` заменяются именами подходящих файлов.
5. **Снятие кавычек**: программа получает аргументы уже без них.

Отсюда три следствия.

**Шаблоны раскрывает оболочка, а не программа.** В команде `ls *.log` программа `ls` не видит звёздочку: она получает готовый список имён. Поэтому шаблоны одинаково работают с любой командой.

**Шаблон без совпадений остаётся как есть.** Фигурные скобки срабатывают всегда, шаблон — только если есть подходящие файлы:

```
echo file{1..3}.txt *.log
```

В пустом каталоге это напечатает `file1.txt file2.txt file3.txt *.log`.

**Переменная без кавычек проходит шаги 3 и 4.** Значение с пробелом распадётся на слова, а значение со звёздочкой превратится в список файлов. Двойные кавычки отключают оба шага, поэтому `"$file"` — всегда один аргумент.

# Присваивание перед командой

Присваивание, стоящее в одной строке перед командой, действует только на неё:

```
LANG=C sort names.txt
```

Переменная `LANG` попадает в окружение одного запуска `sort`, а в самой оболочке не меняется. Так программе задают настройки на один раз.

# Порядок перенаправлений

Перенаправления применяются слева направо, и запись `2>&1` означает «туда, куда поток 1 смотрит в этот момент».

```
ls /nope > out.txt 2>&1
ls /nope 2>&1 > out.txt
```

В первой строке сначала вывод уходит в файл, затем ошибки направляются туда же — в файле окажется всё. Во второй ошибки сначала привязываются к экрану, куда пока смотрит поток 1, и лишь потом вывод уходит в файл. Сообщение об ошибке останется на экране.

# Подстановка процесса

Некоторым программам нужны имена файлов, а у вас есть только вывод команд. Конструкция `<(…)` решает это без временных файлов:

```
diff <(sort a.txt) <(sort b.txt)
```

Оболочка запускает вложенную команду и подставляет на её место путь вида `/dev/fd/63`. Читая этот «файл», `diff` получает вывод `sort`.

# Где выполняется команда

Текущий каталог, переменные и алиасы — свойства конкретного процесса. Важно понимать, в каком процессе выполняется то, что вы написали.

**Скрипт — отдельный процесс.** Если в `go.sh` написано `cd /var/log`, то после `./go.sh` ваш каталог не изменится: каталог сменил дочерний процесс и тут же завершился.

**source выполняет файл в текущей оболочке:**

```
source go.sh
. go.sh
```

Обе записи равнозначны. Теперь `cd` и присваивания из файла подействуют на вашу оболочку. Именно так применяют правки `~/.bashrc`.

**Круглые скобки создают подоболочку** — копию оболочки, изменения в которой наружу не выходят:

```
(cd /tmp && ls)
```

После этой строки вы остались в прежнем каталоге.

**Части конвейера тоже выполняются в подоболочках.** Переменная, изменённая в цикле справа от `|`, после конвейера окажется прежней.

**exec заменяет оболочку программой.** Нового процесса не появляется: оболочка превращается в запущенную программу. После `exec htop` в окне терминала возвращаться некуда, и при выходе из `htop` оно закроется. В скриптах-обёртках последнюю команду запускают через `exec`, чтобы не держать лишний процесс.

# Окружение вне терминала

Файл `~/.bashrc` читают только интерактивные оболочки — те, что открыты в терминале. Команда, которая работает у вас, может не работать там, где терминала нет.

- **cron** запускает задания с почти пустым окружением и коротким `PATH`.
- **Службы systemd** получают только то, что указано в unit-файле.
- **Команда через ssh** — `ssh server команда` — выполняется неинтерактивной оболочкой.

Поэтому в скриптах для таких запусков пишут полные пути к программам и задают нужные переменные явно, в самом скрипте.

# Коды завершения подробно

У кодов есть соглашения, по которым причину сбоя видно без чтения сообщений.

- `0` — успех.
- `1`–`125` — ошибка, смысл определяет сама программа.
- `126` — файл найден, но запустить его нельзя: нет права на исполнение.
- `127` — команда не найдена.
- `128 + N` — программу завершил сигнал с номером N. `130` — это Ctrl+C (сигнал 2), `137` — SIGKILL (сигнал 9), `143` — SIGTERM (сигнал 15).

# Код конвейера

Код конвейера — это код его **последней** команды:

```
false | true
echo $?
```

Будет напечатан `0`, хотя первая команда завершилась ошибкой. В строке `pg_dump db | gzip > db.gz` сбой `pg_dump` останется незамеченным.

Есть два способа это исправить. Массив `PIPESTATUS` хранит коды всех частей последнего конвейера:

```
false | true
echo "${PIPESTATUS[@]}"
```

Это напечатает `1 0`. А режим `pipefail` меняет само правило:

```
set -o pipefail
```

После него конвейер возвращает ошибку, если ошибкой завершилась любая его часть.

# Коротко

- Порядок обработки: скобки, подстановки, разбиение на слова, шаблоны, снятие кавычек.
- Шаблоны раскрывает оболочка; без совпадений шаблон остаётся буквальным.
- Перенаправления читаются слева направо: `> файл 2>&1`, а не наоборот.
- `<(команда)` подставляет вывод команды туда, где ждут имя файла.
- Скрипт и подоболочка не меняют вашу оболочку; `source` меняет; `exec` её заменяет.
- Вне терминала нет `~/.bashrc` и привычного `PATH`.
- 126 — нельзя запустить, 127 — не найдено, больше 128 — сигнал.
- Код конвейера — код последней команды, пока не включён `pipefail`.
