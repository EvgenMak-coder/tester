# Строка процессора в top

Третья строка `top` показывает, на что уходит время процессора. В ней больше ответов, чем во всём остальном выводе.

```
%Cpu(s): 12.0 us, 71.5 sy,  0.0 ni, 15.9 id,  0.3 wa,  0.0 hi,  0.3 si,  0.0 st
```

- `us` (user) — код программ. Высокое значение означает, что программы заняты вычислениями.
- `sy` (system) — код ядра по запросам программ: системные вызовы, работа с сетью и диском, создание процессов.
- `id` (idle) — простой.
- `wa` (iowait) — простой в ожидании ввода-вывода. Процессор свободен, но программы ждут диск.
- `st` (steal) — время, которое гипервизор отдал другим виртуальным машинам.
- `ni` — код процессов с пониженным приоритетом; `hi` и `si` — обработка прерываний.

По этой строке ставят первый диагноз:

- высокий `us` — не хватает процессора, ищите прожорливый процесс;
- высокий `wa` — узкое место в диске;
- высокий `sy` — программа делает слишком много системных вызовов или плодит процессы;
- высокий `st` — проблема вне машины, на стороне хостинга.

В примере выше `sy` заметно больше `us`: процессор занят в основном ядром. Что именно программа у него запрашивает, покажет `strace`.

# Память процесса: RES и VIRT

У каждого процесса в `top` два числа памяти.

- **VIRT** — всё адресное пространство: всё, что процесс запросил или отобразил в память, включая то, чем ни разу не воспользовался.
- **RES** — физическая память, занятая на самом деле.

Реальный расход показывает RES. Гигабайты VIRT при скромном RES — обычное дело и не проблема: программы часто резервируют память с большим запасом.

# Диск: iostat

```
iostat -x 1
```

```
Device   r/s    w/s   r_await  w_await  aqu-sz  %util
sda     12.0  940.0     3.10   182.40   171.3   99.8
```

- `r/s` и `w/s` — операций чтения и записи в секунду;
- `r_await` и `w_await` — сколько миллисекунд в среднем ждёт запрос;
- `aqu-sz` — длина очереди запросов;
- `%util` — доля времени, когда диск был занят.

Диск перегружен, когда занятость близка к 100%, а время ожидания велико. В примере запрос на запись ждёт в среднем 182 мс при очереди в 171 запрос: диск и есть узкое место.

`%util` говорит о занятости во времени, а не о заполненности данными: свободное место показывает `df`.

Найдя перегруженный диск, виновника ищут через `iotop`.

# Системные вызовы: strace

Программа не может сама открыть файл, отправить данные в сеть или запустить другой процесс. Всё это она просит у ядра **системными вызовами**. `strace` показывает каждый такой вызов с аргументами и результатом.

```
strace ./report
strace -p 1234
strace -e trace=openat ./report
```

- без ключей — запустить программу под наблюдением;
- `-p номер` — подключиться к уже работающему процессу, не перезапуская его;
- `-e trace=…` — показывать только выбранные вызовы.

Типичные находки:

```
openat(AT_FDCWD, "/etc/app/config.yml", O_RDONLY) = -1 ENOENT (No such file or directory)
connect(3, {sa_family=AF_INET, sin_port=htons(5432), …}) = -1 ECONNREFUSED
```

Программа молча падает, а `strace` показывает, что она искала файл настроек не там или не смогла подключиться к базе.

Для зависшего процесса смотрят на последнюю строку: незавершённый вызов `read` или `futex` показывает, чего он ждёт. Ctrl+C отсоединяет `strace`, процесс продолжает работу.

# Открытые файлы и порты: lsof

`lsof` перечисляет открытые файлы. В Linux сетевые соединения — тоже файлы, поэтому он отвечает и на сетевые вопросы.

```
sudo lsof -i :8080
sudo lsof -p 1234
sudo lsof /var/log/app.log
```

Первая команда показывает, какой процесс использует порт 8080. С неё начинают, когда служба не стартует с ошибкой «Address already in use». Вторая перечисляет всё, что открыл процесс, третья — кто держит открытым файл.

# Лимиты: ulimit

Для каждого процесса действуют ограничения на ресурсы. Их показывает и задаёт `ulimit`:

```
ulimit -n
ulimit -a
```

`ulimit -n` — предел числа одновременно открытых файлов. Обычное значение — 1024. Сервер, который держит тысячи соединений, быстро в него упирается:

```
Too many open files
```

`ulimit` действует на текущую оболочку и на всё, что из неё запущено. `ulimit -a` показывает все ограничения сразу. Действующие лимиты любого процесса можно прочитать в `/proc/номер/limits`.

# OOM killer

Когда оперативная память и подкачка исчерпаны, выделять больше нечего. Чтобы система не зависла целиком, срабатывает **OOM killer** — механизм ядра, который выбирает процесс и убивает его сигналом SIGKILL.

Жертвой обычно становится самый большой потребитель памяти. Программа при этом не успевает ничего сохранить: со стороны она просто исчезает.

След остаётся в журнале ядра:

```
sudo dmesg | grep -i "out of memory"
```

Если служба внезапно завершилась без единой строки в своём журнале, это первое, что стоит проверить.

# Приоритет диска: ionice

`nice` задаёт приоритет при дележе процессора. У диска свой аналог — `ionice`:

```
ionice -c3 tar -czf /backup/home.tar.gz /home
```

Класс 3 (idle) означает «получать диск только тогда, когда он никому больше не нужен». Тяжёлое копирование не мешает остальным программам. Полностью это работает с планировщиком ввода-вывода BFQ; другие планировщики классы могут не учитывать.

# Коротко

- Строка процессора: `us` — программы, `sy` — ядро, `wa` — ожидание диска, `st` — отнято гипервизором.
- RES — реально занятая память, VIRT — всё адресное пространство.
- `iostat -x`: `%util` под 100 и большой `await` — диск перегружен.
- `strace` показывает системные вызовы; `-p` подключается к работающему процессу.
- `lsof -i :порт` находит, кто занял порт.
- `ulimit -n` — предел открытых файлов; его превышение даёт «Too many open files».
- OOM killer завершает процесс при исчерпании памяти; след — в `dmesg`.
- `ionice -c3` запускает команду с низшим приоритетом доступа к диску.
