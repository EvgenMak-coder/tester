# Как systemd понимает, что служба запущена

systemd следит за процессом, который запустил командой `ExecStart`. Что считать «службой» и когда она «готова», определяет директива `Type`.

- **simple** — значение по умолчанию. Запущенный процесс и есть служба; готовой она считается сразу после запуска.
- **forking** — программа сама уходит в фон: порождает потомка и завершает исходный процесс. Так вели себя демоны старого образца.
- **notify** — программа сама сообщает systemd, что закончила подготовку и готова принимать запросы.
- **oneshot** — программа делает дело и завершается; это не служба, а разовое действие.

Несовпадение типа с поведением программы даёт характерную поломку:

```
[Service]
ExecStart=/opt/legacy/daemon --background
```

Программа уходит в фон, исходный процесс завершается. systemd, считая тип простым, решает, что служба закончила работу, и переводит её в `inactive`, хотя сама программа живёт дальше без присмотра. Лечится двумя способами: указать `Type=forking` либо убрать ключ, чтобы программа оставалась на переднем плане. Второй способ лучше.

# Порядок и зависимость — разные вещи

У связей между юнитами два независимых измерения.

**Порядок** задают `After=` и `Before=`. Они говорят только: если запускаются оба, то в такой последовательности.

**Зависимость** задают `Wants=` и `Requires=`. Они говорят: запуская меня, запусти и его. `Requires` жёстче: если нужный юнит не запустился, не запустится и этот.

```
[Unit]
Requires=postgresql.service
After=postgresql.service
```

Обычно нужны оба. Одно `After` ничего не запустит: если PostgreSQL не включён, приложение стартует без него. Одно `Requires` запустит обе службы одновременно.

И ещё одна оговорка: порядок запуска не означает готовности. «PostgreSQL запущен» не значит «принимает запросы», если его юнит не типа `notify`. Надёжное приложение само повторяет попытки подключения.

# Таймеры

Задание по расписанию в systemd описывают парой юнитов: служба говорит, что делать, таймер — когда.

```
[Timer]
OnCalendar=daily
Persistent=true

[Install]
WantedBy=timers.target
```

Файл `backup.timer` запускает одноимённую службу `backup.service`. `OnCalendar` задаёт расписание: `daily`, `hourly`, `Mon *-*-* 03:00:00`.

`Persistent=true` решает проблему выключенного компьютера: если момент запуска был пропущен, задание выполнится сразу после включения.

Перед cron у таймеров три преимущества: вывод задания попадает в журнал, пропущенные запуски навёрстываются, а задание получает все возможности служб — зависимости, ограничения ресурсов, перезапуск.

```
systemctl list-timers
```

Команда показывает все таймеры, время последнего и следующего срабатывания.

# Активация по сокету

Службу не обязательно держать запущенной. systemd может сам слушать её порт и запустить службу только при первом подключении:

```
sudo systemctl enable --now app.socket
```

Юнит `app.socket` описывает адрес и порт, юнит `app.service` — саму программу. Первое соединение не теряется: systemd принимает его и передаёт службе уже открытым.

Это экономит память на редко используемых службах и позволяет перезапускать службу без отказов: пока она перезапускается, подключения ждут в очереди у systemd.

# Ограничение ресурсов

Каждая служба работает в собственной группе cgroup, и ядро может ограничивать группу целиком, со всеми её процессами.

```
[Service]
MemoryMax=500M
CPUQuota=50%
TasksMax=200
```

- `MemoryMax` — потолок памяти. При превышении ядро убивает процессы внутри группы, не трогая остальную систему;
- `CPUQuota` — доля процессорного времени, 100% соответствует одному ядру;
- `TasksMax` — предел числа процессов и потоков.

Сколько служба потребляет сейчас, показывают `systemctl status` и `systemd-cgtop`.

# Защита служб

Юнит может запереть службу в ограниченном окружении, даже если она работает от root.

```
[Service]
ProtectSystem=strict
ReadWritePaths=/var/lib/app
PrivateTmp=true
NoNewPrivileges=true
```

- `ProtectSystem=strict` — вся файловая система доступна службе только для чтения;
- `ReadWritePaths` — исключения, куда писать можно;
- `PrivateTmp` — собственный, невидимый другим каталог `/tmp`;
- `NoNewPrivileges` — процессы службы не могут получить больше прав, чем имеют.

Взломанная служба с такими настройками не сможет ни изменить систему, ни заглянуть в чужие временные файлы. Оценку защищённости юнита даёт `systemd-analyze security имя`.

# Почему служба перестала перезапускаться

```
app.service: Start request repeated too quickly.
app.service: Failed with result 'exit-code'.
```

У перезапуска есть предохранитель. Если служба падает слишком часто — по умолчанию больше пяти раз за десять секунд, — systemd прекращает попытки, чтобы не нагружать систему бесконечным циклом. Пределы задают `StartLimitBurst` и `StartLimitIntervalSec`.

Сначала находят причину падения в журнале, а затем сбрасывают счётчик:

```
sudo systemctl reset-failed app
sudo systemctl start app
```

# Окружение службы

Служба не наследует ваше окружение. systemd не читает ни `~/.bashrc`, ни `~/.profile`, и переменная, заданная в терминале, до службы не дойдёт. Нужное задают в юните:

```
[Service]
Environment=APP_ENV=production
EnvironmentFile=/etc/app/env
```

`EnvironmentFile` удобен для секретов: файл можно закрыть от чтения всем, кроме root.

# Службы пользователя

Обычный пользователь может держать собственные службы: юниты лежат в `~/.config/systemd/user`, а управляют ими через `systemctl --user`.

У них есть особенность: они работают, пока у пользователя открыт хотя бы один сеанс. После выхода из системы всё останавливается. Чтобы службы пользователя работали всегда, для него включают «задержку»:

```
sudo loginctl enable-linger anna
```

# Что тормозит загрузку

```
systemd-analyze
systemd-analyze blame
```

Первая команда показывает общее время загрузки, вторая — список юнитов, отсортированный по времени запуска. Самые медленные окажутся сверху.

# Коротко

- `Type` должен соответствовать поведению программы; программа, уходящая в фон, требует `forking`.
- `After` — только порядок, `Requires` и `Wants` — запуск; обычно нужны оба.
- Таймер запускает одноимённую службу; `Persistent=true` навёрстывает пропущенное.
- Сокет-юнит запускает службу при первом подключении.
- `MemoryMax`, `CPUQuota` ограничивают службу целиком.
- `ProtectSystem=strict` и `ReadWritePaths` запирают службу в файловой системе.
- «Start request repeated too quickly» — сработал предел перезапусков; `reset-failed` его сбрасывает.
- Переменные задают через `Environment=` и `EnvironmentFile=`.
- Службам пользователя для работы без сеанса нужен `loginctl enable-linger`.
- `systemd-analyze blame` показывает, что замедляет загрузку.
