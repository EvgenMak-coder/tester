# Проброс портов

Соединение SSH может нести не только терминал, но и чужие сетевые соединения. Это называют туннелем или пробросом портов. Видов три, и различаются они тем, где открывается порт.

**Локальный проброс, ключ -L.** Порт открывается на вашем компьютере, а соединения с него выходят наружу со стороны сервера.

```
ssh -L 8080:db.internal:5432 anna@bastion
```

Запись читается так: «мой порт 8080 → через bastion → на db.internal порт 5432». Пока соединение открыто, подключение к `localhost:8080` у вас попадает в базу данных, доступную только из внутренней сети. К базе при этом обращается не ваш компьютер, а `bastion`.

**Обратный проброс, ключ -R.** Всё наоборот: порт открывается на сервере, а соединения приходят к вам.

```
ssh -R 9000:localhost:3000 anna@server
```

Подключение к порту 9000 на сервере попадёт на порт 3000 вашего компьютера. Так показывают коллегам приложение, запущенное на ноутбуке за роутером.

**Динамический проброс, ключ -D.** `ssh -D 1080 anna@server` открывает у вас прокси SOCKS: программы, настроенные на него, выходят в сеть от имени сервера.

Любой проброс живёт, пока открыто соединение SSH. Ключ `-N` открывает туннель без терминала.

# Прыжок через промежуточный узел

Внутренние серверы обычно доступны только с одного узла-привратника — бастиона. Входить на него и оттуда дальше неудобно, и для второго шага на бастионе пришлось бы держать ключи. Ключ `-J` решает это одной командой:

```
ssh -J anna@bastion anna@app.internal
```

Клиент подключается к бастиону, через него открывает канал к цели и уже по этому каналу проходит проверку на конечном сервере. Ключи остаются на вашем компьютере, бастион только пересылает зашифрованный поток.

В `~/.ssh/config` то же самое записывают строкой `ProxyJump bastion`.

# Пересылка агента и её цена

Другой способ ходить дальше с промежуточного узла — пересылка агента, ключ `-A`. Сервер получает канал к вашему агенту и может просить его подписывать запросы на вход.

```
ssh -A anna@shared-server
```

Закрытый ключ при этом ваш компьютер не покидает. Но пока вы подключены, любой, у кого на этом сервере есть права root, может воспользоваться каналом и войти от вашего имени всюду, куда пускает ваш ключ.

Поэтому `-A` включают только для серверов, администраторам которых вы доверяете, а для прыжков используют `-J`: он такой возможности не даёт.

# Ключ сервера изменился

```
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
```

Ключ сервера не совпал с записанным в `known_hosts`. Причин две: сервер переустановили или заменили, либо между вами и сервером кто-то встал.

Правильный порядок — сначала выяснить причину: спросить у администратора, сверить отпечаток ключа по другому каналу. И только убедившись, что всё в порядке, удалить старую запись:

```
ssh-keygen -R server.example.com
```

Удалять весь `known_hosts` или отключать проверку параметром `StrictHostKeyChecking=no` нельзя: предупреждение существует именно для этого случая.

# Менять настройки sshd и не потерять доступ

Ошибка в `sshd_config` на удалённом сервере может оставить вас снаружи. Безопасная последовательность такая:

```
sudo sshd -t
sudo systemctl reload ssh
```

1. `sshd -t` проверяет файл на ошибки и ничего не меняет. Молчание означает, что файл в порядке.
2. `reload` заставляет службу перечитать настройки. Уже открытые сеансы при этом не обрываются.
3. Не закрывая текущий сеанс, открывают **второй** и убеждаются, что вход работает.

Текущий сеанс — страховка: если новый вход не удался, через него всё можно вернуть.

# Ключ есть, а сервер просит пароль

Самая частая причина — права на файлы на сервере. `sshd` отказывается читать `authorized_keys`, если его или каталог над ним мог изменить кто-то посторонний. Клиенту он об этом не говорит, а в журнал сервера пишет:

```
sshd[2291]: Authentication refused: bad ownership or modes for directory /home/anna/.ssh
```

Исправление:

```
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

Проверяются и права самого домашнего каталога: он не должен быть доступен на запись группе и остальным. Владельцем всех трёх должен быть сам пользователь.

# Ограничить ключ

Перед ключом в `authorized_keys` можно записать ограничения. Такой ключ годится для одной задачи и ни для чего больше:

```
command="/usr/local/bin/backup.sh",no-port-forwarding,no-pty ssh-ed25519 AAAAC3Nz... backup@nas
```

- `command="…"` — при входе с этим ключом выполняется только эта команда, что бы ни запросил клиент;
- `no-port-forwarding` — туннели запрещены;
- `no-pty` — терминал не выделяется, оболочку открыть нельзя;
- `from="10.0.0.0/8"` — ключ принимается только с этих адресов.

Так оформляют ключи для автоматики: сервер резервного копирования может запустить копирование, но, даже украденный, его ключ не даёт доступа к оболочке.

# Одно соединение на много сеансов

Каждое подключение SSH начинается с обмена ключами и проверки, это заметная доля секунды. Если вы часто подключаетесь к одному серверу, соединение можно использовать повторно:

```
Host *
    ControlMaster auto
    ControlPath ~/.ssh/cm-%r@%h:%p
    ControlPersist 10m
```

Первое подключение становится главным. Следующие `ssh`, `scp` и `rsync` к тому же серверу идут через него мгновенно, без новой проверки. `ControlPersist` держит главное соединение открытым ещё десять минут после закрытия последнего сеанса.

# Сеанс зависает от простоя

Роутеры и межсетевые экраны забывают о соединениях, по которым долго ничего не передаётся. Сеанс SSH после нескольких минут тишины замирает. Лечится настройкой клиента:

```
Host *
    ServerAliveInterval 60
```

Клиент раз в минуту отправляет серверу пустой запрос по зашифрованному каналу, и соединение остаётся «живым» для всех устройств на пути.

# Коротко

- `-L порт:узел:порт` — порт у вас, выход со стороны сервера; `-R` — наоборот; `-D` — прокси SOCKS.
- `ssh -J бастион цель` — вход через промежуточный узел без ключей на нём.
- Пересылка агента `-A` позволяет администратору сервера действовать от вашего имени.
- При смене ключа сервера сначала выясняют причину, потом `ssh-keygen -R имя`.
- `sshd -t`, затем `reload`, затем проверка вторым сеансом.
- Права: `~/.ssh` — 700, `authorized_keys` — 600; причина отказа — в журнале сервера.
- `command=` и `no-pty` в `authorized_keys` ограничивают ключ одной задачей.
- `ControlMaster` ускоряет повторные подключения, `ServerAliveInterval` не даёт сеансу зависнуть.
