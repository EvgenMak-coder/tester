# Коды ответа как диагноз

Когда сайт за обратным прокси не работает, код ответа сразу говорит, где искать.

- **404** — nginx не нашёл файл или подходящее правило. Проблема в путях.
- **403** — доступ запрещён: права на файлы, отсутствие индексного файла или SELinux.
- **502 Bad Gateway** — nginx работает, но не получил ответ от приложения: оно упало, не запущено или слушает не тот порт.
- **504 Gateway Timeout** — приложение есть, но отвечает слишком долго.
- **503** — служба временно недоступна: перегрузка или обслуживание.

Главное в 502 и 504: их отдаёт сам прокси, значит он жив. Искать нужно за ним.

```
sudo tail /var/log/nginx/error.log
sudo ss -tlnp | grep 3000
systemctl status app
```

Журнал ошибок nginx называет причину прямо: «connection refused» — приложение не слушает, «upstream timed out» — не успело ответить.

# reload и restart при ошибке в настройках

В настройках nginx допущена ошибка. Что будет дальше, зависит от команды.

`systemctl reload nginx` — главный процесс сначала проверяет новые настройки. Найдя ошибку, он оставляет прежние рабочие процессы. Команда вернёт ошибку, но сайт продолжит работать со старыми настройками, и посетители ничего не заметят.

`systemctl restart nginx` — сервер останавливается, а запуститься с ошибочными настройками не может. Сайт лежит, пока ошибку не исправят.

Поэтому на рабочем сервере настройки применяют через `reload`, а перед ним всё равно выполняют `nginx -t`.

# Цепочка сертификатов

Сертификат сайта подписан не корневым центром напрямую, а **промежуточным**; тот, в свою очередь, подписан корневым. Клиент знает только корневые. Чтобы он мог проверить всю цепочку, сервер обязан прислать промежуточные сертификаты сам.

Если он этого не делает, возникает странная картина: в браузерах сайт открывается, а другие программы отказываются.

```
curl: (60) SSL certificate problem: unable to get local issuer certificate
```

Браузеры умеют добывать недостающее звено самостоятельно и помнят виденные раньше. `curl`, библиотеки языков программирования и мобильные приложения — нет.

Причина почти всегда одна: в настройках указан файл только с сертификатом сайта. certbot кладёт рядом два файла, и нужен второй:

```
ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;
```

`fullchain.pem` содержит сертификат сайта вместе с промежуточными, `cert.pem` — только сертификат сайта.

# Проверка TLS из командной строки

Посмотреть, что сервер отдаёт на самом деле, позволяет `openssl`:

```
openssl s_client -connect example.com:443 -servername example.com
```

Команда устанавливает соединение TLS и печатает цепочку сертификатов и параметры шифрования. Ключ `-servername` нужен, когда на адресе несколько сайтов: без него сервер может вернуть сертификат другого сайта.

Срок действия сертификата достают так:

```
echo | openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -dates
```

Этой строкой удобно проверять сертификаты в скриптах наблюдения.

# Настоящий адрес клиента

Приложение за обратным прокси во всех запросах видит один и тот же адрес — `127.0.0.1`. Это не ошибка: соединение с приложением устанавливает nginx, и приложение видит его адрес.

Настоящий адрес прокси передаёт в заголовках:

```
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

Приложение читает адрес из `X-Forwarded-For`. Заголовок `X-Forwarded-Proto` сообщает, пришёл ли исходный запрос по HTTPS: без него приложение считает, что работает по HTTP, и строит неверные ссылки.

Доверять этим заголовкам приложение должно только от своего прокси. Клиент может прислать любой заголовок сам, и если приложение доступно в обход прокси, адрес легко подделать.

# Тонкости DNS: CNAME и TTL

**CNAME и корень зоны.** Запись CNAME означает «это имя — полный псевдоним другого», и рядом с ней у того же имени не может быть никаких других записей. Для поддоменов вроде `www` это не мешает. Но у корня зоны — самого `example.com` — обязательно есть записи SOA и NS. Поэтому CNAME для корня создать нельзя. Провайдеры DNS обходят это собственными типами записей: ALIAS, ANAME или «сглаживанием» CNAME.

**TTL и переезды.** У каждой записи есть TTL — время, на которое её можно запомнить. Пока оно не истекло, кэширующие серверы по всему миру отдают старый ответ и к вам за новым не обращаются.

Отсюда картина после переезда сайта: запись A изменили, а часть посетителей ещё сутки попадает на старый сервер. Правильный порядок переезда:

1. За день-два снизить TTL записи до нескольких минут.
2. Дождаться, пока истечёт старое значение TTL.
3. Изменить запись.
4. Старый сервер не выключать, пока на него приходят запросы.
5. Вернуть TTL к обычному значению.

# NFS: root_squash

NFS доверяет клиенту: тот сообщает номер пользователя, и сервер применяет права этого номера. Без защиты администратор любой клиентской машины был бы полноправным root и на сервере: мог бы читать чужие файлы и создавать программы с SUID.

```
/srv/share 192.168.1.0/24(rw,sync,root_squash)
```

Параметр `root_squash` действует по умолчанию: запросы от root клиента выполняются с правами пользователя nobody. Обратный параметр, `no_root_squash`, включают осознанно и редко.

Из того же доверия следует, что номера пользователей на клиенте и сервере должны совпадать. Если anna на одной машине имеет UID 1000, а на другой 1001, её файлы на общем каталоге будут принадлежать кому-то другому.

# Samba: два слоя прав

В настройках общей папки указано `writable = yes`, а пользователь не может создать файл. Samba работает с файлами от имени вошедшего пользователя, и обычные права Linux никуда не деваются.

Действуют оба слоя, и итог определяет более строгий:

1. настройки папки в `smb.conf` — что разрешает Samba;
2. права файловой системы — что разрешает Linux.

Разрешение в `smb.conf` не поможет, если каталог принадлежит root с правами 755. Проверяют сам каталог: `ls -ld /srv/share`. Настройки проверяет команда `testparm`.

# Почта: SPF, DKIM, DMARC

Протокол электронной почты не проверяет отправителя: любой сервер может отправить письмо от имени любого домена. Три записи DNS закрывают эту дыру.

**SPF** перечисляет серверы, которым разрешено отправлять почту от имени домена:

```
example.com.  TXT  "v=spf1 mx ip4:203.0.113.25 -all"
```

Запись читается: разрешены серверы из MX-записей домена и указанный адрес; `-all` в конце означает «всех остальных отклонять».

**DKIM** — электронная подпись письма. Сервер-отправитель подписывает письмо закрытым ключом, открытый лежит в DNS, и получатель проверяет, что письмо не изменено и подписано владельцем домена.

**DMARC** говорит получателю, что делать с письмами, не прошедшими проверки: пропускать, отправлять в спам или отклонять, и куда присылать отчёты.

Без этих записей письма домена часто попадают в спам, а его адрес может подделать кто угодно.

# Коротко

- 502 — приложение за прокси не ответило, 504 — отвечает слишком долго; причина в `error.log`.
- `reload` при ошибке в настройках оставляет сайт работать, `restart` его останавливает.
- Сервер должен отдавать промежуточные сертификаты: в nginx указывают `fullchain.pem`.
- `openssl s_client -connect узел:443` показывает, какой сертификат отдаётся.
- Настоящий адрес клиента прокси передаёт в `X-Forwarded-For`.
- CNAME нельзя создать для корня зоны; перед переездом заранее снижают TTL.
- `root_squash` лишает root клиента особых прав на сервере NFS.
- В Samba действуют и настройки папки, и права файловой системы.
- SPF — кто может отправлять, DKIM — подпись письма, DMARC — что делать с непрошедшими проверку.
