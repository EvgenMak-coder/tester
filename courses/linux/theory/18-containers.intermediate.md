# Запуск в фоне и порты

Простой `docker run nginx` занимает терминал и ни к чему не подключён снаружи. Рабочий запуск выглядит иначе:

```
docker run -d --name web -p 8080:80 nginx
```

**Ключ -d** запускает контейнер в фоне: Docker печатает идентификатор и сразу возвращает управление терминалу. Без него вывод программы шёл бы на экран, а Ctrl+C останавливал бы контейнер.

**Ключ -p** пробрасывает порт. Сеть у контейнера своя, и его порты снаружи недоступны, пока вы этого не попросите. Запись читается слева направо: **порт хоста : порт контейнера**. Здесь порт 8080 хоста ведёт на порт 80 внутри контейнера, и сайт открывается по адресу `http://localhost:8080`.

Порядок легко перепутать. Помогает правило: слева то, что снаружи.

# Остановленные контейнеры

Контейнер, программа в котором завершилась, не исчезает. Он переходит в остановленное состояние и из вывода `docker ps` пропадает.

```
docker ps -a
```

Ключ `-a` показывает все контейнеры, включая остановленные. В столбце STATUS виден код завершения: `Exited (1) 2 minutes ago`.

Это первый шаг, когда контейнер «не запускается»: на самом деле он запустился и сразу завершился с ошибкой. Дальше смотрят, что программа успела вывести: `docker logs имя`.

Чтобы контейнер удалялся сам после остановки, добавляют ключ `--rm`.

# Войти в контейнер

```
docker exec -it web bash
```

`docker exec` запускает дополнительную команду в уже работающем контейнере. Ключи `-i` и `-t` подключают клавиатуру и терминал, так что получается обычная оболочка внутри контейнера.

Это инструмент диагностики: посмотреть файлы, проверить настройки, убедиться, что нужная программа видна. Выход из оболочки контейнер не останавливает: его главный процесс продолжает работу.

Во многих образах нет `bash`: тогда пробуют `sh`. Одну команду можно выполнить без входа: `docker exec web ls /etc/nginx`.

# Данные и тома

Контейнер пишет изменения в собственный тонкий слой поверх образа. Остановку и запуск этот слой переживает. Удаление контейнера — нет: всё, что было создано внутри, пропадает вместе с ним.

А удаляют контейнеры постоянно: обновление программы — это удаление старого контейнера и создание нового из свежего образа. Поэтому всё, что должно сохраняться, выносят в **тома**.

```
docker run -d -v pgdata:/var/lib/postgresql/data postgres:17
```

Запись после `-v` читается так: том `pgdata` подключить к каталогу `/var/lib/postgresql/data` внутри контейнера. Том — хранилище вне контейнера, которым управляет Docker. Контейнер можно удалить и создать заново, данные базы останутся.

Вместо имени тома можно указать каталог хоста:

```
docker run -d -v /srv/site:/usr/share/nginx/html:ro nginx
```

Тогда контейнер видит обычный каталог с диска. Приписка `:ro` делает его доступным только для чтения.

# Dockerfile

Собственный образ описывают текстовым файлом с именем `Dockerfile`. Это список инструкций, которые выполняются по порядку:

```
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "server.py"]
```

- `FROM` — образ, взятый за основу;
- `WORKDIR` — рабочий каталог для следующих инструкций;
- `COPY` — скопировать файлы из каталога сборки в образ;
- `RUN` — выполнить команду при сборке, обычно установить что-то;
- `CMD` — команда, которая запускается при старте контейнера.

Важно различать `RUN` и `CMD`. `RUN` выполняется один раз, когда образ собирают, и его результат становится частью образа. `CMD` ничего не выполняет при сборке: он лишь записывает, что запускать потом.

# Сборка образа

```
docker build -t myapp:1.0 .
```

Команда выполняет инструкции из `Dockerfile` и сохраняет результат как образ.

- `-t myapp:1.0` задаёт имя и тег;
- точка в конце — **каталог сборки**: в нём ищется `Dockerfile`, и из него берутся файлы для `COPY`.

Всё содержимое каталога сборки передаётся Docker. Лишнее — каталог `.git`, зависимости, секреты — исключают файлом `.dockerignore`.

# Docker Compose

Настоящее приложение редко состоит из одного контейнера: рядом с ним база данных, кэш, обратный прокси. Запускать их длинными командами по одному неудобно. Compose описывает всё в одном файле `compose.yaml`:

```
services:
  app:
    build: .
    ports:
      - "8080:8000"
    depends_on:
      - db
  db:
    image: postgres:17
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:
```

```
docker compose up -d
docker compose logs -f
docker compose down
```

`up -d` создаёт недостающее и запускает все службы в фоне. `down` останавливает и удаляет контейнеры; тома при этом остаются.

Службы одного файла находятся в общей сети и видят друг друга по именам: приложение обращается к базе по адресу `db`.

# Podman

Docker состоит из двух частей: команды `docker` и фоновой службы, которая работает от root и делает всю работу. Это удобно, но служба с правами root — лишняя поверхность для атаки.

**Podman** устроен иначе: фоновой службы нет, контейнеры запускаются прямо от имени пользователя, без прав root. Команды почти совпадают:

```
podman run -d -p 8080:80 nginx
podman ps
podman build -t myapp .
```

Образы и реестры у них общие: формат стандартизован. Podman входит в состав Fedora и RHEL и поставляется там вместо Docker.

# Коротко

- `-d` запускает в фоне, `-p хост:контейнер` пробрасывает порт.
- `docker ps -a` показывает и остановленные контейнеры с кодом завершения.
- `docker exec -it имя bash` открывает оболочку в работающем контейнере.
- Данные вне тома пропадают при удалении контейнера; `-v том:путь` их сохраняет.
- `Dockerfile`: `FROM`, `COPY`, `RUN` — при сборке, `CMD` — при запуске.
- `docker build -t имя:тег .` собирает образ из текущего каталога.
- `docker compose up -d` запускает все службы из `compose.yaml`.
- Podman работает без фоновой службы и без прав root; команды те же.
