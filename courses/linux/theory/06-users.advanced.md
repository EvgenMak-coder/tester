# Точные правила sudoers

Правило «разрешить всё» удобно, но часто нужно обратное: дать одному человеку одно действие. Строка sudoers состоит из четырёх частей:

```
anna ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx
```

- `anna` — **кто**. Имя пользователя или группа со знаком процента.
- `ALL=` — **на каких узлах**. Имеет смысл, когда один файл раздают на много серверов; обычно `ALL`.
- `(ALL)` — **от чьего имени**. Здесь от любого пользователя, включая root.
- **что** — список команд через запятую, с полными путями.

`NOPASSWD:` перед командой отменяет запрос пароля. Это нужно для скриптов и систем автоматизации, которым пароль ввести некому.

Команда вместе с аргументами должна совпасть целиком. Это правило разрешает anna перезапускать nginx, но `systemctl stop nginx` или `systemctl restart sshd` под него не подпадают.

Выдавая точные правила, стоит помнить о лазейках: если разрешить через `sudo` редактор или `less`, из них можно запустить оболочку с правами root. Разрешать нужно конкретные действия, а не программы общего назначения.

Собственные правила кладут в `/etc/sudoers.d/` и правят через `visudo -f`, а проверяют командой `sudo -l -U anna`.

# sudo и перенаправление

Эта команда не сработает, хотя запущена через `sudo`:

```
sudo echo "nameserver 1.1.1.1" > /etc/resolv.conf
```

Ответ — «Permission denied». Перенаправление выполняет не `echo`, а ваша оболочка, причём ещё до запуска `sudo`. Файл пытается открыть обычный пользователь, а с правами root выполняется только `echo`.

Есть два рабочих способа:

```
echo "nameserver 1.1.1.1" | sudo tee /etc/resolv.conf
sudo sh -c 'echo "nameserver 1.1.1.1" > /etc/resolv.conf'
```

В первом файл открывает `tee`, запущенный от root; с ключом `-a` он дописывает в конец. Во втором от root запускается целая оболочка, и перенаправление выполняет уже она.

# su и su -

`su` открывает оболочку от имени другого пользователя. Разница между двумя формами — в окружении.

```
su postgres
su - postgres
```

Без дефиса меняется только пользователь. Переменные окружения, `PATH` и текущий каталог остаются от прежнего. Программы могут искать настройки в чужом домашнем каталоге и вести себя неожиданно.

С дефисом запускается оболочка входа: окружение строится заново, как если бы пользователь вошёл сам, а текущим каталогом становится его домашний. Почти всегда нужна именно эта форма.

`su` спрашивает пароль **целевого** пользователя, `sudo` — ваш. Поэтому там, где у root нет пароля, вместо `su -` используют `sudo -i`: он даёт такую же оболочку входа.

# PAM: кто на самом деле проверяет вход

Программы `login`, `sshd`, `sudo`, `su` не проверяют пароли сами. Они обращаются к **PAM** — набору подключаемых модулей. Какие модули вызывать и в каком порядке, описано в каталоге `/etc/pam.d/`, по файлу на программу.

Модули делятся на четыре вида по тому, когда они срабатывают:

- `auth` — проверка личности: пароль, ключ, одноразовый код;
- `account` — можно ли входить: не истёк ли срок, не заблокирована ли запись;
- `password` — правила смены пароля;
- `session` — что сделать при открытии и закрытии сеанса.

Через PAM настраивается то, что касается всех способов входа сразу:

- `pam_faillock` — блокировка после нескольких неудачных попыток;
- `pam_pwquality` — требования к сложности пароля;
- `pam_limits` — ограничения ресурсов из `/etc/security/limits.conf`.

Счётчик неудач и снятие блокировки — у команды `faillock`: `faillock --user anna --reset`.

> Ошибка в файлах PAM может закрыть вход всем, включая root. Перед правкой открывают второй сеанс с правами root и не закрывают его, пока новый вход не проверен.

# Сроки действия паролей

Сроки из `/etc/shadow` показывает и меняет команда `chage`:

```
sudo chage -l anna
sudo chage -M 90 anna
sudo chage -d 0 anna
```

- `-M 90` — пароль нужно менять не реже чем раз в 90 дней;
- `-m 1` — не чаще чем раз в день;
- `-W 7` — предупреждать за семь дней;
- `-E 2026-12-31` — дата, после которой учётная запись перестаёт действовать;
- `-d 0` — потребовать смену пароля при следующем входе.

# Что видно в /etc/shadow

По второму полю можно понять состояние учётной записи, не запуская команд:

```
boris:!$y$j9T$Qw1...:19990:0:99999:7:::
```

- хеш начинается с `!` — пароль заблокирован командой `passwd -l` или `usermod -L`;
- на месте хеша стоит только `*` или `!` — пароль не задан, войти по паролю нельзя. Так выглядят служебные учётные записи;
- поле пустое — пароль не требуется вовсе. Это почти всегда ошибка.

# Системные учётные записи

Учётную запись для службы создают с ключом `-r`:

```
sudo useradd -r -s /usr/sbin/nologin prometheus
```

Она получает UID из системного диапазона, обычно меньше 1000, а домашний каталог для неё не создаётся. Границы диапазонов заданы в `/etc/login.defs`.

Никаких особых прав системный номер не даёт. Это только соглашение: такие записи не показываются на экране входа и не смешиваются с людьми.

# Заготовка домашнего каталога

Когда `useradd -m` создаёт домашний каталог, он копирует в него содержимое `/etc/skel`. Положив туда готовый `.bashrc` или каталог с инструкциями, администратор получает одинаковые начальные настройки у всех новых пользователей. На уже существующих это не влияет.

# Группа новых файлов

Новый файл получает **основную** группу того, кто его создал. Дополнительные группы на это не влияют.

Отсюда частая проблема общих каталогов: коллеги из группы `dev` создают файлы, но каждый файл получает личную группу автора, и остальным он недоступен. Решений два: бит SGID на каталоге, с которым группа наследуется от каталога, или временная смена основной группы командой `newgrp dev`.

# Пользователи не из /etc/passwd

В организациях учётные записи часто хранятся централизованно: в LDAP или Active Directory. Тогда пользователь входит на сервер, но в локальном файле его нет:

```
grep maria /etc/passwd
getent passwd maria
```

Первая команда ничего не найдёт. Вторая найдёт: `getent` опрашивает все источники, которые система использует на самом деле.

Список источников и их порядок записаны в `/etc/nsswitch.conf`:

```
passwd: files sss
```

Эта строка означает: сначала локальные файлы, потом служба SSSD, которая обращается к каталогу организации. Тем же способом `getent group` и `getent hosts` проверяют группы и имена узлов.

# Коротко

- Строка sudoers: кто, где, от чьего имени, какие команды. Команда с аргументами должна совпасть целиком.
- `sudo` не действует на перенаправление; используют `sudo tee` или `sudo sh -c`.
- `su -` даёт окружение целевого пользователя, `su` без дефиса — оставляет прежнее.
- Вход проверяет PAM; блокировку после неудач даёт `pam_faillock`.
- `chage` управляет сроками пароля; `chage -d 0` требует сменить его при входе.
- `!` перед хешем в shadow — пароль заблокирован.
- `useradd -r` создаёт служебную учётную запись без домашнего каталога.
- `/etc/skel` — образец домашнего каталога.
- `getent passwd имя` находит учётную запись в любом источнике, не только в `/etc/passwd`.
