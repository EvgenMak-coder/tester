# Как ядро проверяет доступ

Когда процесс открывает файл, ядро выбирает **одну** тройку прав и смотрит только на неё.

1. Если процесс принадлежит владельцу файла — берётся тройка владельца.
2. Иначе, если процесс входит в группу файла — тройка группы.
3. Иначе — тройка остальных.

Найдя подходящую категорию, ядро на ней останавливается. Права не складываются.

Отсюда неожиданное следствие: владелец может иметь меньше прав, чем его же группа.

```
----rw---- 1 anna dev 512 Oct  7 10:00 draft.txt
```

Если anna — владелец и одновременно участник dev, прочитать файл она не сможет: для неё проверяется только первая тройка, а она пуста. Другие участники dev — смогут. Правда, anna как владелец может вернуть себе права через `chmod`.

На root проверки чтения и записи не действуют вовсе. Исключение — запуск: чтобы root мог выполнить файл, право `x` должно быть хотя бы у кого-то.

# Весь путь до файла

Чтобы открыть `/srv/data/app/config.yml`, нужно право на сам файл и право `x` на **каждый** каталог по пути: `/`, `/srv`, `/srv/data` и `/srv/data/app`. Право `r` на каталогах при этом не требуется: оно нужно только для просмотра списка.

Поэтому проверка одного `ls -l` на файл часто ничего не объясняет. Всю цепочку разом показывает `namei`:

```
namei -l /srv/data/app/config.yml
```

Команда выводит права каждого каталога на пути, и закрытое звено видно сразу.

# ACL: когда трёх категорий мало

Обычные права знают одного владельца и одну группу. Если нужно дать доступ ещё одному человеку или второй группе, используют списки доступа — ACL.

```
setfacl -m u:boris:rw plan.md
getfacl plan.md
```

Первая команда даёт пользователю boris чтение и запись. Вторая показывает весь список:

```
user::rw-
user:boris:rw-
group::r--
mask::rw-
other::---
```

О наличии ACL говорит знак `+` в конце прав в выводе `ls -l`.

# Маска ACL

Строка `mask` — верхняя граница для всех записей ACL, кроме владельца и остальных. Если в маске нет права, его не получит никто из перечисленных поимённо, что бы ни было написано в его строке:

```
user:boris:rw-    #effective:r--
mask::r--
```

Запись обещает boris чтение и запись, но действует только чтение. Комментарий `effective` показывает итог.

Маску легко сузить случайно: у файла с ACL команда `chmod g-w` меняет именно её. Вернуть её можно так:

```
setfacl -m m::rw plan.md
```

Чтобы новые файлы в каталоге получали ACL автоматически, каталогу задают список по умолчанию: `setfacl -d -m g:dev:rwX /srv/project`.

# Возможности вместо SUID

SUID даёт программе все права root сразу. Часто нужно гораздо меньше. **Возможности** (capabilities) делят всемогущество root на отдельные права, которые выдаются поштучно.

Типичный пример — веб-сервер, который должен слушать порт 80, но работать от обычного пользователя. Порты ниже 1024 может занимать только root, однако для этого есть отдельная возможность:

```
sudo setcap cap_net_bind_service=+ep /usr/local/bin/server
getcap /usr/local/bin/server
```

Программа сможет занять порт 80 и ничего больше: ни читать чужие файлы, ни менять настройки системы.

Попутно стоит знать: **на скрипты SUID не действует.** Ядро Linux игнорирует этот бит для файлов, которые выполняет интерпретатор, потому что между запуском интерпретатора и чтением файла скрипт можно подменить. Если скрипту нужны права root, для него пишут точное правило в sudoers.

# Атрибуты: запрет даже для root

Отдельно от прав у файла есть атрибуты файловой системы. Самый известный — `i`, immutable:

```
sudo chattr +i /etc/resolv.conf
lsattr /etc/resolv.conf
```

Файл с этим атрибутом нельзя изменить, переименовать или удалить никому, включая root:

```
rm: cannot remove '/etc/resolv.conf': Operation not permitted
```

Ни `ls -l`, ни владелец, ни права этого не объяснят: атрибуты показывает только `lsattr`. Снимается запрет командой `chattr -i`.

Второй полезный атрибут — `a`, только дописывание: в файл можно добавлять данные, но нельзя менять или стирать уже записанное. Его ставят на журналы.

# Параметры монтирования

Некоторые ограничения задаются для файловой системы целиком и действуют поверх любых прав.

- **noexec** — с этой файловой системы нельзя запускать программы.
- **nosuid** — биты SUID и SGID на ней игнорируются.
- **ro** — запись запрещена всем.

Типичный случай: скрипт в `/tmp` имеет право `x`, но не запускается с «Permission denied». Причина — параметр `noexec`:

```
findmnt /tmp
```

Запуск через интерпретатор — `bash /tmp/run.sh` — при этом работает: интерпретатор лежит на другой файловой системе, а скрипт он просто читает.

# Порядок поиска причины

Когда доступ запрещён, а причина не очевидна, удобно идти от простого к редкому.

1. Кто вы для этого файла: владелец, участник группы или остальной? Это показывают `id` и `ls -l`.
2. Есть ли право `x` на всех каталогах пути: `namei -l путь`.
3. Нет ли ACL и сужающей маски: `getfacl файл`.
4. Нет ли атрибута immutable: `lsattr файл`.
5. Как смонтирована файловая система: `findmnt каталог`.
6. Не вмешивается ли SELinux или AppArmor — о них рассказывает модуль «Безопасность».

# Коротко

- Ядро берёт одну тройку: владелец, иначе группа, иначе остальные. Права не суммируются.
- Нужен `x` на каждом каталоге пути; цепочку показывает `namei -l`.
- ACL добавляет права отдельным пользователям и группам; маска ограничивает их сверху.
- Возможности дают программе одно конкретное право root вместо всех.
- На скрипты SUID не действует.
- Атрибут `i` запрещает изменения даже root; его видно только в `lsattr`.
- `noexec` и `nosuid` действуют поверх прав файла.
