# Как выбирается маршрут

Для каждого исходящего пакета ядро решает, через какой интерфейс и какому узлу его отдать. Решение принимается по таблице маршрутов:

```
default via 192.168.1.1 dev eth0
10.0.0.0/8 via 172.16.0.1 dev eth1
10.20.0.0/16 dev tun0
```

Правило одно: из всех подходящих записей выбирается **самая точная** — та, у которой длиннее префикс. Адрес `10.20.3.4` подходит под все три строки, но `/16` точнее, чем `/8`, а `default` — это `/0`. Пакет уйдёт через `tun0`.

Порядок строк в таблице значения не имеет. Маршрут по умолчанию используется, только когда ничего точнее не нашлось.

Спросить у ядра, что оно выберет для конкретного адреса, можно напрямую:

```
ip route get 10.20.3.4
```

Команда ничего не отправляет в сеть: она показывает интерфейс, шлюз и адрес источника, которые будут использованы. На серверах с несколькими интерфейсами и VPN это самый быстрый способ понять, куда идёт трафик.

# Пересылка и NAT

Обычный компьютер пакеты, адресованные не ему, отбрасывает. Чтобы машина с двумя интерфейсами стала маршрутизатором, пересылку включают параметром ядра:

```
sysctl net.ipv4.ip_forward
sudo sysctl -w net.ipv4.ip_forward=1
```

Этого достаточно, когда обе сети знают друг о друге. Но частные адреса в интернете не маршрутизируются: ответ на пакет с адресом `192.168.1.15` не найдёт дорогу обратно. Поэтому на выходе в интернет адрес источника подменяют:

```
sudo iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
```

Правило заменяет адрес источника у пакетов, уходящих через `eth0`, адресом самого `eth0`. Маршрутизатор запоминает, кто что отправил, и возвращает ответы нужному узлу. Так целая сеть выходит в интернет через один адрес. Пересылка плюс это правило — и есть домашний роутер.

# VLAN

VLAN делит одну физическую сеть на несколько изолированных, помечая кадры номером. Узлы разных VLAN не видят друг друга, хотя подключены к одному коммутатору.

```
sudo ip link add link eth0 name eth0.100 type vlan id 100
```

Команда создаёт виртуальный интерфейс поверх `eth0`. Всё, что отправлено через `eth0.100`, получает метку 100; принимает он только кадры с такой же меткой. Порт коммутатора при этом должен пропускать помеченные кадры — работать в режиме trunk.

# Мост

Мост — программный коммутатор внутри ядра. Он соединяет несколько интерфейсов в одну сеть на уровне кадров.

Главное применение — виртуализация. На сервере создают мост `br0`, подключают к нему физический интерфейс и виртуальные интерфейсы машин. Машины оказываются в той же сети, что и сам сервер, и получают адреса от общего DHCP. IP-адрес сервера при этом переносят с физического интерфейса на мост.

# Перехват пакетов: tcpdump

Когда догадок недостаточно, смотрят на сами пакеты.

```
sudo tcpdump -i eth0 -nn port 53
sudo tcpdump -i any -nn host 203.0.113.10 and port 443
```

- `-i` — интерфейс, `any` означает все;
- `-nn` — не превращать адреса в имена, а номера портов в названия служб. Вывод точнее, и сам `tcpdump` не порождает лишних запросов DNS;
- в конце — фильтр: порт, узел, протокол, соединённые через `and` и `or`.

Ключ `-w файл` сохраняет пакеты для разбора в Wireshark.

# Установка соединения TCP

Соединение TCP открывается тремя пакетами: клиент шлёт SYN, сервер отвечает SYN-ACK, клиент подтверждает ACK. В `tcpdump` флаги видны в квадратных скобках: `[S]` — SYN, `[S.]` — SYN-ACK, `[.]` — ACK, `[R]` — сброс, `[F]` — завершение.

По первым пакетам видно, что не так:

```
IP 10.0.0.5.51234 > 203.0.113.10.443: Flags [S], seq 1880, length 0
IP 10.0.0.5.51234 > 203.0.113.10.443: Flags [S], seq 1880, length 0
IP 10.0.0.5.51234 > 203.0.113.10.443: Flags [S], seq 1880, length 0
```

Клиент повторяет SYN и не получает ничего. Пакеты теряются: их отбрасывает межсетевой экран, сервер выключен, либо ответу нет обратного пути. Клиент увидит «timed out».

Если бы порт был просто закрыт, сервер ответил бы пакетом с флагом `[R]`, и клиент получил бы «Connection refused».

# MTU и крупные пакеты

У каждого канала есть предел размера пакета — MTU, обычно 1500 байт. Туннели и VPN добавляют свои заголовки, поэтому внутри них помещается меньше.

Когда пакет слишком велик, маршрутизатор должен сообщить отправителю сообщением ICMP «нужна фрагментация», и тот уменьшит пакеты. Но ICMP часто блокируют целиком. Тогда появляется характерная картина: `ping` проходит, вход по SSH работает, а передача больших файлов и некоторые сайты зависают. Мелкие пакеты проходят, крупные молча теряются.

Проверяют это пингом с запретом фрагментации:

```
ping -M do -s 1472 адрес
```

1472 байта данных плюс 28 байт заголовков дают ровно 1500. Если такой пакет не проходит, а меньший проходит — дело в MTU. Лечат уменьшением MTU на интерфейсе туннеля или ограничением размера сегмента на маршрутизаторе.

# Диагностика DNS: dig и getent

`dig` обращается к серверам DNS напрямую и показывает ответ целиком:

```
dig example.com
dig +short example.com MX
dig @1.1.1.1 example.com
```

`+short` оставляет только ответ, тип записи указывают после имени, а через `@` спрашивают конкретный сервер.

Но обычные программы узнают адреса иначе — через системную библиотеку, которая следует порядку из `/etc/nsswitch.conf` и сначала смотрит в `/etc/hosts`. Отсюда расхождение: `ping db` работает, а `dig db` ничего не находит. Имя записано в `/etc/hosts`, а `dig` туда не заглядывает.

Что получит обычная программа, показывает `getent`:

```
getent hosts db
```

Правило простое: `dig` — чтобы проверить DNS, `getent hosts` — чтобы проверить, что увидит приложение.

# Коротко

- Из подходящих маршрутов выбирается самый точный; `ip route get адрес` показывает выбор ядра.
- Маршрутизатором машину делает `net.ipv4.ip_forward=1`, выход в интернет через один адрес — правило MASQUERADE.
- VLAN изолирует сети метками, мост соединяет интерфейсы как коммутатор.
- `tcpdump -i интерфейс -nn фильтр` показывает пакеты.
- Повторяющийся SYN без ответа — пакеты отбрасываются; ответ `[R]` — порт закрыт.
- Мелкое проходит, крупное виснет — проверьте MTU: `ping -M do -s 1472`.
- `dig` спрашивает DNS напрямую, `getent hosts` показывает то, что видят программы.
