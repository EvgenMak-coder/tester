# Из чего сделан контейнер

Контейнер — не отдельная технология ядра, а сочетание двух механизмов, которые существуют сами по себе.

**Пространства имён** (namespaces) отвечают за изоляцию. Каждое пространство даёт процессу собственный вид на один из ресурсов:

- `pid` — свои номера процессов: главный процесс контейнера видит себя с номером 1;
- `mnt` — свои точки монтирования, то есть своя файловая система;
- `net` — свои сетевые интерфейсы, адреса и порты;
- `uts` — своё имя узла;
- `user` — свои номера пользователей: root внутри может быть обычным пользователем снаружи.

**cgroups** отвечают за ресурсы: ограничивают и учитывают процессор, память и ввод-вывод для группы процессов.

Первое определяет, что контейнер видит, второе — сколько он может потребить. С хоста процесс контейнера виден как обычный процесс: его показывает `ps`, и ему можно послать сигнал.

# chroot

Предшественник контейнеров — `chroot`. Он меняет процессу корневой каталог: программа видит другое дерево файлов и считает его всей системой.

Но изоляция этим и ограничивается. Процессы, сеть и пользователи остаются общими, а root внутри способен из такого окружения выбраться. Контейнер добавляет к смене корня изоляцию остальных ресурсов и ограничения.

`chroot` остаётся удобным для своей исходной задачи — починки системы. Загрузившись с установочного носителя, монтируют корневой раздел и «входят» в него, чтобы переустановить загрузчик или сменить пароль.

# Слои образа и кэш сборки

Образ состоит из слоёв. Каждая инструкция `Dockerfile` создаёт слой, и Docker кэширует его. При пересборке слой берётся из кэша, пока не изменились сама инструкция и всё, что выше неё. Стоит одному слою измениться — все следующие собираются заново.

Отсюда частая ошибка:

```
FROM node:22
WORKDIR /app
COPY . .
RUN npm install
CMD ["node", "server.js"]
```

Любая правка любого файла меняет слой `COPY . .`, и `npm install` выполняется заново, хотя зависимости не менялись. Правильный порядок — от редко меняющегося к часто меняющемуся:

```
COPY package.json package-lock.json ./
RUN npm install
COPY . .
```

Теперь зависимости ставятся заново, только когда изменился их список. Сборка после правки кода занимает секунды.

Слои одного образа общие для всех контейнеров, запущенных из него, а собственные изменения каждый контейнер пишет в свой тонкий верхний слой.

# ENTRYPOINT и CMD

Обе инструкции задают, что запускается в контейнере, но по-разному реагируют на аргументы `docker run`.

- Аргументы после имени образа **заменяют** `CMD` целиком.
- К `ENTRYPOINT` они **дописываются**.

```
ENTRYPOINT ["python", "manage.py"]
CMD ["runserver"]
```

`docker run образ` выполнит `python manage.py runserver`. `docker run образ migrate` выполнит `python manage.py migrate`. Обычное разделение: `ENTRYPOINT` — сама программа, `CMD` — её аргументы по умолчанию.

# Главный процесс и сигналы

Контейнер живёт ровно столько, сколько его главный процесс — тот, что имеет номер 1 внутри. Отсюда два следствия.

**Контейнер без долгоживущей программы завершается сразу.** `docker run -d ubuntu` запускает `bash` без терминала; тот читает конец ввода и выходит. Контейнер — не маленький сервер, а обёртка вокруг одной программы.

**Сигнал остановки получает только главный процесс.** `docker stop` шлёт SIGTERM процессу номер 1, ждёт десять секунд и убивает всё через SIGKILL. Если главный процесс — оболочка, а приложение запущено из неё, сигнал до приложения не доходит:

```
#!/bin/sh
./migrate.sh
node server.js
```

Оболочка сигнал дочернему процессу не передаёт. `docker stop` каждый раз ждёт все десять секунд, а приложение погибает, не закрыв соединения. Исправление — одно слово:

```
exec node server.js
```

`exec` заменяет оболочку программой: теперь `node` сам становится процессом номер 1 и получает сигнал.

По той же причине в `Dockerfile` предпочитают запись в квадратных скобках: `CMD ["node", "server.js"]`. Запись строкой `CMD node server.js` запускает программу через оболочку.

# Сети и имена

В Docker несколько видов сетей, и главное различие между ними — умеют ли контейнеры находить друг друга по имени.

В стандартной сети `bridge`, куда контейнеры попадают по умолчанию, они общаются только по IP-адресам. Адреса выдаются при запуске и меняются при пересоздании.

В сети, созданной пользователем, работает встроенный DNS:

```
docker network create appnet
docker run -d --name db --network appnet postgres:17
docker run -d --name app --network appnet myapp
```

Контейнер `app` обращается к базе просто по имени `db`. Compose создаёт такую сеть для каждого проекта сам, поэтому там службы видят друг друга без настройки.

Проброс портов через `-p` нужен только для доступа **снаружи**. Между собой контейнеры одной сети общаются напрямую, и порт базы данных на хост открывать незачем.

# Группа docker — это root

Служба Docker работает от root и выполняет то, что просит клиент. Тот, кто может ей приказывать, может всё:

```
docker run -v /:/host -it ubuntu bash
```

Команда подключает корень хоста внутрь контейнера. Внутри вы root и видите всю файловую систему хоста в `/host`: можно читать `/etc/shadow`, править sudoers, подкладывать ключи SSH.

Поэтому участие в группе `docker` равно правам root. В неё включают только тех, кому доверили бы `sudo` без пароля. Работа контейнеров без root, как в Podman, устраняет эту проблему в корне.

Отсюда же правило для образов: программа в контейнере не должна работать от root. Пользователя задаёт инструкция `USER` в `Dockerfile`.

# Лимиты и код 137

По умолчанию контейнер может занять все ресурсы хоста. Ограничения задают при запуске:

```
docker run -d --memory=512m --cpus=1.5 myapp
```

Это те же cgroups. При превышении лимита памяти ядро убивает процесс внутри контейнера, и он завершается с характерным кодом:

```
Exited (137) 2 minutes ago
```

Код больше 128 означает гибель от сигнала: 137 = 128 + 9, то есть SIGKILL. Причин обычно две: превышен лимит памяти либо программа не отреагировала на SIGTERM и была добита через десять секунд. Различить их помогает `docker inspect`: в первом случае там стоит `OOMKilled: true`.

Код 143 = 128 + 15 означает, что программа завершилась по SIGTERM, то есть остановилась штатно.

# KVM и аппаратная виртуализация

Когда нужна настоящая виртуальная машина со своим ядром, в Linux используют **KVM** — модуль ядра, который превращает его в гипервизор. Ему нужна поддержка процессора:

```
grep -Ec '(vmx|svm)' /proc/cpuinfo
```

`vmx` — признак технологии Intel VT-x, `svm` — AMD-V. Команда считает строки с этими флагами. Ноль означает, что аппаратная виртуализация недоступна: процессор её не поддерживает либо она выключена в настройках UEFI.

Ноль будет и внутри виртуальной машины, если хост не разрешил вложенную виртуализацию. Машинами управляют через `virsh`: `virsh list --all` показывает их список.

# Коротко

- Контейнер — это пространства имён (изоляция) и cgroups (ресурсы).
- `chroot` меняет только корень файловой системы.
- Инструкции `Dockerfile` образуют слои; редко меняющееся ставят выше, чтобы работал кэш.
- Аргументы `docker run` заменяют `CMD` и дописываются к `ENTRYPOINT`.
- Контейнер живёт, пока жив процесс номер 1; сигнал остановки получает только он — используйте `exec`.
- Имена контейнеров разрешаются только в сетях, созданных пользователем.
- Группа `docker` равна правам root.
- Код 137 — SIGKILL: превышен лимит памяти или процесс не остановился вовремя.
- Для KVM нужны флаги `vmx` или `svm` в `/proc/cpuinfo`.
