# Порядок правил

Правила межсетевого экрана проверяются по порядку, сверху вниз. Первое подошедшее решает судьбу пакета, остальные не рассматриваются. Отсюда классическая ошибка:

```
iptables -A INPUT -j DROP
iptables -A INPUT -p tcp --dport 22 -j ACCEPT
```

Ключ `-A` дописывает правило в конец цепочки. Первое правило отбрасывает всё, и до второго не доходит ни один пакет. SSH работать не будет.

Правильный порядок — сначала разрешения, в конце общий запрет. Вставить правило в начало цепочки позволяет ключ `-I`. Действующий порядок показывает `iptables -L -n --line-numbers`.

В современных системах на смену `iptables` пришёл `nftables` с командой `nft`, но принцип тот же.

# Состояние соединений

Экран помнит установленные соединения и может отличить ответ на ваш запрос от непрошеного пакета. На этом держится правило, которое есть в любом наборе:

```
ct state established,related accept
```

Оно пропускает пакеты уже установленных соединений и связанных с ними. Без него при политике «входящие запрещены» сервер не получал бы ответы на собственные исходящие запросы: не скачивались бы обновления, не работал бы DNS.

Благодаря этому правилу остальные можно писать только для **новых** соединений: «разрешить новые подключения на порт 443», не думая об ответных пакетах.

# DROP и REJECT

Запретить соединение можно двумя способами.

- **DROP** молча отбрасывает пакет. Отправитель ничего не получает и ждёт до истечения времени ожидания.
- **REJECT** отбрасывает пакет и отвечает отказом. Отправитель сразу видит «Connection refused».

Снаружи порт, закрытый через DROP, выглядит как выключенный узел. Для внешней границы обычно выбирают DROP: сканеру не сообщают ничего и заставляют его ждать. Для внутренней сети удобнее REJECT: свои программы получают отказ мгновенно, а не висят в ожидании.

При диагностике это различие — подсказка: «timed out» означает, что где-то стоит DROP или нет маршрута, «refused» — что пакет дошёл и получил явный отказ.

# Метки SELinux

SELinux принимает решения не по путям, а по **меткам**. У каждого файла и процесса есть контекст, и политика говорит, процессы какого типа могут обращаться к файлам какого типа.

```
ls -Z /var/www/html
ps -eZ | grep nginx
```

Ключ `-Z` показывает контекст. У файлов сайта тип `httpd_sys_content_t`, и веб-серверу разрешено их читать.

Типичная поломка: файлы сайта создали в домашнем каталоге и перенесли командой `mv` в `/var/www/html`. Права в порядке, а nginx отвечает 403. Причина — `mv` в пределах одной файловой системы сохраняет метку, и у файлов остался тип `user_home_t`, читать который веб-серверу запрещено.

```
sudo restorecon -Rv /var/www/html
```

`restorecon` выставляет метки, положенные каталогу по политике. Команда `cp`, в отличие от `mv`, создаёт новые файлы, и они сразу получают правильную метку.

# Где искать отказы SELinux

Отказы записывает подсистема аудита в `/var/log/audit/audit.log`. Нужные записи имеют тип AVC:

```
sudo ausearch -m avc -ts recent
sudo ausearch -m avc -ts recent | audit2why
```

`ausearch` отбирает отказы за последние минуты, `audit2why` объясняет человеческим языком, почему действие запрещено и что с этим можно сделать.

Часто достаточно включить готовый переключатель политики. Например, разрешить веб-серверу исходящие соединения:

```
sudo setsebool -P httpd_can_network_connect on
```

# Аудит: кто менял файл

Подсистема аудита умеет следить за файлами и системными вызовами.

```
sudo auditctl -w /etc/passwd -p wa -k passwd_changes
sudo ausearch -k passwd_changes
```

- `-w` — за каким файлом наблюдать;
- `-p wa` — за какими действиями: `w` — запись, `a` — изменение атрибутов, ещё есть `r` — чтение и `x` — запуск;
- `-k` — метка, по которой записи потом находят.

Вторая команда покажет, кто, когда и какой программой менял файл. Аудит ничего не запрещает, он только записывает. Правила из командной строки действуют до перезагрузки; постоянные кладут в `/etc/audit/rules.d/`.

# Настройка fail2ban

Собственные настройки fail2ban пишут в файл `/etc/fail2ban/jail.local`, чтобы их не затёрло обновление:

```
[sshd]
enabled  = true
maxretry = 5
findtime = 10m
bantime  = 1h
```

- `maxretry` — сколько неудачных попыток допускается;
- `findtime` — за какое время они считаются;
- `bantime` — на сколько блокируется адрес.

Читается так: адрес, с которого за десять минут было пять неудачных входов, блокируется на час.

```
sudo fail2ban-client status sshd
sudo fail2ban-client set sshd unbanip 203.0.113.7
```

Первая команда показывает заблокированные адреса, вторая снимает блокировку — пригодится, если заблокировали вас самих.

# LUKS: пароль и ключ

Данные на разделе LUKS зашифрованы не вашим паролем, а случайным **мастер-ключом**. Он хранится в заголовке раздела, зашифрованный паролем.

Из этого следуют три практических вывода.

**Смена пароля мгновенна.** На разделе в 2 ТБ она занимает секунды: перешифровывается одна запись в заголовке, а не данные.

```
sudo cryptsetup luksChangeKey /dev/sdb1
sudo cryptsetup luksAddKey /dev/sdb1
```

**Паролей может быть несколько.** В заголовке несколько слотов, и в каждом — свой пароль к одному мастер-ключу. У двух администраторов могут быть разные пароли, и отозвать один можно, не трогая другой.

**Заголовок нужно беречь.** Если он повреждён, данные не расшифровать даже с верным паролем. Его копию сохраняют командой `cryptsetup luksHeaderBackup`.

# Подписи gpg

Контрольная сумма подтверждает целостность, но не авторство. Подпись подтверждает оба свойства: файл не изменён и подписан владельцем определённого ключа.

```
gpg --verify archive.tar.gz.sig archive.tar.gz
```

```
gpg: Good signature from "Release Team <release@example.org>"
gpg: WARNING: This key is not certified with a trusted signature!
```

Первая строка говорит, что подпись верна: архив подписан этим ключом и не изменён. Вторая — о другом: `gpg` не знает, вправду ли ключ принадлежит названному автору. Ключ с таким именем может создать кто угодно.

Это проверяют, сверив **отпечаток** ключа с опубликованным в надёжном источнике: на сайте проекта, в документации. `BAD signature` вместо первой строки означает, что файл повреждён или подменён.

# Поиск программ с SUID

Программа с битом SUID выполняется с правами владельца файла. Если владелец — root, её ошибка даёт права root тому, кто её запустил. Поэтому список таких программ проверяют при любом аудите:

```
find / -perm -4000 -type f 2>/dev/null
```

`-perm -4000` отбирает файлы с установленным SUID, `2>/dev/null` убирает сообщения о недоступных каталогах.

В чистой системе список короткий и предсказуемый: `passwd`, `sudo`, `su`, `mount` и несколько других. Его сохраняют и сравнивают при следующих проверках. Незнакомый файл с SUID в `/tmp` или домашнем каталоге — либо ошибка настройки, либо лазейка, оставленная взломщиком.

# Коротко

- Правила проверяются по порядку; общий запрет ставят последним.
- `ct state established,related accept` пропускает ответы на собственные запросы.
- DROP молчит, REJECT отвечает отказом.
- SELinux решает по меткам; `mv` сохраняет старую метку, `restorecon` выставляет правильную.
- Отказы SELinux — в `audit.log`, тип AVC; `ausearch -m avc` и `audit2why`.
- `auditctl -w файл -p wa -k метка` записывает изменения файла.
- fail2ban: `maxretry` неудач за `findtime` — блокировка на `bantime`.
- В LUKS пароль защищает мастер-ключ: смена мгновенна, паролей может быть несколько.
- Good signature подтверждает целостность; принадлежность ключа проверяют по отпечатку.
- `find / -perm -4000` находит программы с SUID.
