# Обратный прокси

Современное веб-приложение — отдельная программа, которая сама слушает какой-нибудь порт, например 3000. Выставлять её в интернет напрямую не принято. Перед ней ставят **обратный прокси**: сервер, который принимает запросы клиентов и передаёт их приложению.

Клиенты видят только прокси, обычно nginx на портах 80 и 443. Он берёт на себя общие заботы:

- шифрование: TLS настраивается в одном месте;
- отдачу статических файлов без участия приложения;
- распределение запросов между несколькими экземплярами приложения;
- ограничение нагрузки и размеров запросов.

Само приложение слушает внутренний порт на `127.0.0.1` и снаружи недоступно.

Слово «обратный» отличает его от обычного прокси. Обычный стоит на стороне клиентов и выпускает их в интернет. Обратный стоит на стороне серверов и принимает запросы из интернета.

# Устройство настроек nginx

Настройки nginx лежат в `/etc/nginx`. Они состоят из вложенных блоков, и два из них главные.

```
server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
    }

    location /static/ {
        root /var/www/example;
    }
}
```

**server** описывает один сайт: на каком порту слушать и на какое имя отзываться.

**location** описывает, что делать с запросами по определённому пути. Здесь всё, что начинается с `/static/`, отдаётся с диска, а остальное передаётся приложению.

Директива `proxy_pass` и делает nginx обратным прокси: он сам обращается к приложению и возвращает клиенту его ответ. Браузер об адресе `127.0.0.1:3000` ничего не узнаёт.

# Проверить и применить

```
sudo nginx -t
sudo systemctl reload nginx
```

`nginx -t` читает все файлы настроек и сообщает, где ошибка, либо отвечает «test is successful». Ничего при этом не применяется. Эту проверку выполняют перед каждым применением.

`reload` заставляет nginx перечитать настройки, не обрывая текущих соединений.

Если что-то не работает, смотрят два журнала: `/var/log/nginx/access.log` — все запросы, и `/var/log/nginx/error.log` — ошибки.

# Несколько сайтов на одном адресе

Один сервер с одним IP-адресом может обслуживать сколько угодно сайтов. Для каждого пишут свой блок `server` с собственным `server_name`.

Различает их nginx по заголовку **Host**: браузер в каждом запросе сообщает, к какому имени он обращается. nginx находит блок с подходящим `server_name` и обрабатывает запрос по его правилам.

Для HTTPS имя нужно знать ещё раньше, до расшифровки запроса, чтобы выбрать сертификат. Браузер сообщает его при установке соединения — это расширение называется SNI.

# Бесплатные сертификаты

**Let's Encrypt** — удостоверяющий центр, который выдаёт сертификаты бесплатно и автоматически. Браузеры им доверяют. Получает сертификаты программа **certbot**:

```
sudo certbot --nginx -d example.com
```

Чтобы выдать сертификат, центр должен убедиться, что вы управляете доменом. certbot сам проходит эту проверку, получает сертификат и вписывает его в настройки nginx.

Сертификаты выдаются на 90 дней. Это не неудобство, а расчёт на автоматизацию: certbot ставит таймер и продлевает их сам. Проверить, что продление сработает, можно так:

```
sudo certbot renew --dry-run
```

# Записи DNS

Зона домена состоит из записей разных типов. Основные:

- **A** — имя → адрес IPv4;
- **AAAA** — имя → адрес IPv6;
- **CNAME** — имя — псевдоним другого имени;
- **MX** — какие серверы принимают почту для домена;
- **TXT** — произвольный текст; в нём хранят служебные данные, например для проверки владения доменом;
- **NS** — какие серверы отвечают за зону.

```
dig +short example.com A
dig +short example.com MX
```

Чтобы сайт открывался по имени, нужна запись A, указывающая на адрес сервера. Чтобы на домен приходила почта — запись MX. Отправляющий сервер спрашивает MX-записи домена получателя и доставляет письмо на сервер с наименьшим числом приоритета.

# NFS: экспорт и монтирование

На сервере каталоги, которые он раздаёт, перечислены в файле `/etc/exports`:

```
/srv/share  192.168.1.0/24(rw,sync)
```

Строка читается так: каталог `/srv/share` открыт для узлов сети `192.168.1.0/24` на чтение и запись. После правки настройки применяют командой `sudo exportfs -ra`.

На клиенте каталог монтируют:

```
sudo mount -t nfs files:/srv/share /mnt/share
```

Источник записывается как `сервер:каталог`. Файлы никуда не копируются: они остаются на сервере и читаются по сети по мере обращения.

Чтобы подключение восстанавливалось при загрузке, строку добавляют в `/etc/fstab` с параметрами `_netdev,nofail`: первый велит ждать сеть, второй не даёт загрузке остановиться, если сервер недоступен.

Что экспортирует сервер, показывает `showmount -e files`.

# chrony

Службой времени в большинстве дистрибутивов служит chrony. У неё есть команда для проверки:

```
chronyc tracking
chronyc sources
```

`tracking` показывает, с каким сервером сверяются часы и насколько они расходятся с эталоном (строка System time). `sources` перечисляет все серверы времени; звёздочкой отмечен тот, по которому идёт синхронизация.

chrony подводит часы плавно, слегка ускоряя или замедляя их. Резкий скачок времени ломает программы, которые измеряют интервалы.

# Коротко

- Обратный прокси принимает запросы клиентов и передаёт их приложениям за ним.
- В nginx блок `server` — сайт, блок `location` — правило для пути; `proxy_pass` передаёт запрос приложению.
- `nginx -t` проверяет настройки, `systemctl reload nginx` применяет их.
- Сайты на одном адресе различаются по заголовку Host и директиве `server_name`.
- certbot получает и сам продлевает сертификаты Let's Encrypt.
- A — адрес, CNAME — псевдоним, MX — почта, TXT — текст.
- NFS: сервер перечисляет каталоги в `/etc/exports`, клиент монтирует `сервер:каталог`.
- `chronyc tracking` показывает расхождение часов.
