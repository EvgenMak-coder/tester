# Почему скрипт не работает из cron

Скрипт отлажен в терминале, добавлен в расписание — и не работает. Почти всегда причина в окружении: cron запускает задания не так, как ваш терминал.

- **Короткий PATH.** Обычно только `/usr/bin` и `/bin`. Программы из `/usr/local/bin` и `/snap/bin` не находятся, и скрипт завершается с «command not found».
- **Файлы оболочки не читаются.** `~/.bashrc` и `~/.profile` для cron не существуют, поэтому заданных там переменных нет.
- **Другой каталог.** Задание стартует в домашнем каталоге пользователя, и относительные пути ведут не туда.
- **Другая оболочка.** По умолчанию команды выполняет `/bin/sh`, а не bash.

Лечится всё это явностью. В начале таблицы задают нужные переменные:

```
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
```

а в самих скриптах пишут полные пути и переходят в нужный каталог первой строкой.

# Знак процента

```
0 1 * * * tar -czf /backup/site-$(date +%F).tar.gz /srv/site
```

Эта строка выглядит правильной и не работает. В таблице cron знак `%` имеет особый смысл: он означает перевод строки, а всё после первого такого знака передаётся команде на стандартный ввод. Команда обрывается на `date +`.

Знак нужно экранировать обратной косой чертой: `date +\%F`. Надёжнее вынести команду в скрипт и вызывать из таблицы только его: в скрипте у процента обычный смысл.

# Куда девается вывод

Всё, что задание выводит на экран, cron отправляет письмом владельцу таблицы или по адресу из переменной `MAILTO`. На сервере без почтовой службы письмо уйти не может, и вывод теряется вместе с сообщениями об ошибках.

Поэтому вывод перенаправляют сами:

```
0 2 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1
```

Запись `2>&1` направляет в тот же файл и ошибки. Без неё в журнале окажется только обычный вывод, а самое нужное пропадёт.

Запускал ли cron задание вообще, видно в системном журнале: `journalctl -u cron`.

# День месяца и день недели

```
0 0 1 * 1 /usr/local/bin/monthly.sh
```

Интуиция подсказывает: «в полночь первого числа, если это понедельник». На самом деле cron ведёт себя иначе. Когда заданы и день месяца, и день недели, задание запускается при совпадении **любого** из них: первого числа каждого месяца и ещё каждый понедельник.

«Первый понедельник месяца» выражают по-другому: ограничивают дни диапазоном, а день недели проверяют в самой команде.

```
0 0 1-7 * * [ "$(date +\%u)" = 1 ] && /usr/local/bin/monthly.sh
```

# Не запускать дважды

Задание запускается каждую минуту, но иногда работает дольше. Тогда второй экземпляр стартует, пока жив первый, они мешают друг другу, а при постоянной перегрузке их число растёт лавиной.

Защищает от этого `flock`:

```
* * * * * flock -n /run/lock/sync.lock /usr/local/bin/sync.sh
```

`flock` берёт блокировку на файл и выполняет команду. Если блокировка занята, с ключом `-n` он сразу выходит. Блокировка снимается сама, когда процесс завершается, — даже если его убили. Этим она надёжнее самодельных файлов-флажков, которые остаются после сбоя и блокируют всё навсегда.

# Снимки на жёстких ссылках

Хранить полную копию за каждый день дорого, а цепочка инкрементных неудобна при восстановлении. У `rsync` есть способ получить лучшее от обоих:

```
rsync -a --link-dest=/backup/2026-10-06 /srv/site/ /backup/2026-10-07/
```

Создаётся новый каталог на сегодня. Изменившиеся файлы копируются в него как обычно. Для неизменённых вместо копии создаётся жёсткая ссылка на тот же файл во вчерашнем каталоге.

Результат: каждый каталог выглядит как полная копия, и восстановить любой день можно простым копированием. А место на диске занимают только изменившиеся файлы: остальные — те же данные под ещё одним именем. Старый каталог можно удалить, не повредив остальные: данные живут, пока на них есть хоть одна ссылка.

# Образ диска: dd

`dd` копирует данные байт за байтом, не разбираясь, что внутри. Ему всё равно, файл это, раздел или целый диск.

```
sudo dd if=/dev/sda of=/dev/sdb bs=4M status=progress
sudo dd if=/dev/sda of=/backup/sda.img bs=4M status=progress
```

- `if` — откуда читать (input file);
- `of` — куда писать (output file);
- `bs` — размер блока: с крупным блоком копирование идёт быстрее;
- `status=progress` — показывать ход работы.

Первая команда переносит весь диск на другой, вместе с таблицей разделов и загрузчиком. Вторая сохраняет образ диска в файл.

> `dd` не задаёт вопросов. Перепутав `if` и `of`, вы затрёте исходный диск содержимым пустого. Имена устройств перед запуском сверяют по `lsblk`.

Недостаток образа — он копирует и пустое место, поэтому занимает столько же, сколько весь диск.

# Копии баз данных

Каталог работающей базы данных нельзя копировать как обычные файлы. База пишет в несколько файлов согласованно, а `tar` или `rsync` читают их по очереди, в разные моменты. Копия получается внутренне противоречивой: она либо не восстановится, либо восстановится с испорченными данными. И обнаружится это в самый неподходящий момент.

Правильных способов три:

- **логическая выгрузка** средствами самой базы: `pg_dump`, `mysqldump`. Результат — согласованный текстовый файл;
- **штатное физическое копирование**, например `pg_basebackup`;
- **снимок тома** — LVM или файловой системы: все файлы фиксируются в один момент.

То же касается любых программ, которые держат данные в нескольких связанных файлах.

# Правило 3-2-1

Надёжность резервного копирования описывают тремя числами:

- **3** экземпляра данных: оригинал и две копии;
- **2** разных носителя или хранилища — на случай общего дефекта;
- **1** экземпляр в другом месте — на случай пожара, кражи или шифровальщика, который добрался до всей сети.

К этому добавляют четвёртое требование: регулярно проверять восстановление. Раз в несколько месяцев копию разворачивают на чистой машине и убеждаются, что из неё получается рабочая система. Только так обнаруживаются забытые каталоги, несогласованные базы и архивы, которые не открываются.

# Абсолютные пути в архиве

```
sudo tar -czf /backup/etc.tar.gz /etc
```

При создании архива GNU tar убирает из путей начальную косую черту и сообщает об этом: `Removing leading '/' from member names`. В архиве файлы записаны как `etc/…`, а не `/etc/…`.

Поэтому при распаковке они попадают в подкаталог текущего каталога, а не поверх системы. Это защита: распаковав архив, чтобы достать один файл, вы не затрёте действующие настройки. Вернуть абсолютные пути может только ключ `-P`.

# Коротко

- У cron короткий `PATH`, нет `~/.bashrc`, оболочка — `/bin/sh`; пути и переменные задают явно.
- `%` в crontab — перевод строки; пишут `\%` или выносят команду в скрипт.
- Вывод заданий уходит в почту; перенаправляйте: `>> файл 2>&1`.
- День месяца и день недели объединяются через «или».
- `flock -n файл команда` не даёт запустить второй экземпляр.
- `rsync --link-dest` даёт ежедневные полные копии ценой одних изменений.
- `dd if=откуда of=куда` копирует диск целиком и не прощает ошибок.
- Базы данных копируют выгрузкой или снимком, а не файлами.
- 3-2-1: три экземпляра, два носителя, один в другом месте, и проверка восстановления.
- `tar` убирает начальную косую черту, архив распаковывается в текущий каталог.
