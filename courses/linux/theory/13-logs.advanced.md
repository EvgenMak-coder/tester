# Размер журнала systemd

Журнал systemd растёт, пока не упрётся в предел. По умолчанию предел — десятая часть раздела, и на большом диске это гигабайты.

Сократить журнал немедленно можно двумя способами:

```
sudo journalctl --vacuum-size=500M
sudo journalctl --vacuum-time=2weeks
```

Первая команда удаляет самые старые записи, пока общий размер не уложится в 500 МБ, вторая — всё старше двух недель.

Чтобы журнал не вырастал снова, предел задают в `/etc/systemd/journald.conf`:

```
[Journal]
SystemMaxUse=500M
```

После правки службу перезапускают: `sudo systemctl restart systemd-journald`.

# Журнал, который не переживает перезагрузку

Где хранится журнал, определяет параметр `Storage` в том же файле.

- `persistent` — на диске, в `/var/log/journal`.
- `volatile` — в памяти, в `/run/log/journal`. После перезагрузки ничего не остаётся.
- `auto` — на диске, если каталог `/var/log/journal` существует, иначе в памяти.

Последнее значение — источник загадки: `journalctl -b -1` отвечает, что предыдущих загрузок нет, и причину сбоя, после которого сервер перезагрузился, найти негде. Журнал вёлся в памяти. Лечится созданием каталога или явной настройкой:

```
sudo mkdir -p /var/log/journal
sudo systemctl restart systemd-journald
```

# Ротация и открытые файлы

После ротации приложение продолжает писать в старый, переименованный файл `app.log.1`, а новый `app.log` остаётся пустым. Причина в том, как работают открытые файлы.

Программа пишет не по имени, а по дескриптору — он привязан к самому файлу. Переименование меняет только имя в каталоге. Программа об этом не узнаёт и продолжает писать туда же.

У logrotate два решения.

**Сообщить программе.** После ротации выполняется команда, которая просит программу переоткрыть журнал:

```
/var/log/app/*.log {
    daily
    rotate 7
    postrotate
        systemctl reload app
    endscript
}
```

**Не переименовывать вовсе.** Параметр `copytruncate` копирует содержимое в новый файл, а исходный обрезает до нуля. Программа ничего не замечает. Это подходит программам, которые не умеют переоткрывать журнал, но несколько строк, записанных между копированием и обрезкой, теряются.

# Сбор журналов на одном сервере

Когда серверов много, журналы собирают в одном месте. Причин две: удобно искать по всем сразу, и взломщик, получивший доступ к машине, не сможет стереть следы, которые уже ушли с неё.

В rsyslog пересылка — одна строка:

```
*.*  @@logs.example.com:514
```

`*.*` означает все источники и все уровни. Число знаков `@` выбирает протокол: одна — UDP, две — TCP. UDP проще, но теряет сообщения при перегрузке сети, поэтому для журналов предпочитают TCP.

# Вывод для программ

Запись журнала systemd — не строка, а набор полей: текст, уровень, номер процесса, имя юнита, точное время и десятки других. Обычный вывод показывает малую часть.

```
journalctl -u app -o json
journalctl -u app -o json-pretty -n 1
journalctl -u app -o cat
```

- `-o json` — каждая запись одной строкой JSON со всеми полями. Такой вывод разбирают программами, например `jq`;
- `-o json-pretty` — то же, но с отступами, чтобы прочитать глазами;
- `-o cat` — только текст сообщений, без времени и имени узла.

По любому полю можно отбирать: `journalctl _PID=1234`, `journalctl _UID=1000`.

# Прошлое: sar

`top`, `vmstat` и `iostat` показывают только настоящее. На вопрос «почему сервер тормозил вчера ночью» они не ответят.

Пакет `sysstat` содержит службу, которая каждые десять минут сохраняет показатели системы, и команду `sar`, которая достаёт их из архива:

```
sar -u
sar -r
sar -d
sar -u -f /var/log/sysstat/sa06
```

- `-u` — процессор;
- `-r` — память;
- `-d` — диски;
- `-f файл` — данные за другой день: число в имени файла — день месяца.

Условие одно: сбор должен быть включён заранее. После происшествия ставить пакет поздно.

# Как читать vmstat

```
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b    swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 2  3 2097148  61200   1024  83500 4200 5100  4400  5300  900 1800  6  9 20 65  0
```

Первая строка вывода `vmstat` — среднее с момента загрузки, смотреть нужно на следующие.

- `r` — процессы, ждущие процессор. Если это число стабильно больше числа ядер, процессора не хватает.
- `b` — процессы, ждущие ввод-вывод.
- `si` и `so` — объём, читаемый из подкачки и записываемый в неё за секунду. В здоровой системе там нули.
- `bi` и `bo` — чтение и запись на диски.
- `us`, `sy`, `id`, `wa` — доли времени процессора: программы, ядро, простой, ожидание диска.

В примере память исчерпана: `free` и `cache` малы, а `si` и `so` исчисляются тысячами — идёт непрерывный обмен с подкачкой. Процессор 65% времени простаивает в ожидании диска (`wa`). Это картина нехватки памяти, а не процессора.

# Потерянные сообщения

```
systemd-journald[412]: Suppressed 14235 messages from app.service
```

journald ограничивает поток от каждой службы: по умолчанию не более 10 000 сообщений за 30 секунд. Лишние отбрасываются, а в журнале остаётся такая запись.

Обычно это признак беды в самом приложении: оно зациклилось на ошибке и пишет одно и то же тысячи раз в секунду. Если поток законный, пределы поднимают параметрами `RateLimitBurst` и `RateLimitIntervalSec` в `journald.conf`.

# Время в журналах

Сопоставлять журналы разных серверов можно только при точных часах. Если записи об одном событии расходятся на минуты, первым делом проверяют синхронизацию:

```
timedatectl
```

В выводе важна строка `System clock synchronized: yes`. Часовой пояс влияет только на то, как время показывается; расхождение в минутах — это неточные часы. Для вывода журнала в едином времени есть ключ `journalctl --utc`.

# Коротко

- `journalctl --vacuum-size=500M` сокращает журнал сейчас, `SystemMaxUse=` — ограничивает навсегда.
- Без каталога `/var/log/journal` журнал живёт в памяти и теряется при перезагрузке.
- После ротации программа пишет в старый файл; нужен `postrotate` или `copytruncate`.
- В rsyslog `@@сервер` — пересылка по TCP, `@сервер` — по UDP.
- `-o json` выводит записи со всеми полями.
- `sar` показывает нагрузку в прошлом, если сбор был включён заранее.
- В `vmstat` ненулевые `si` и `so` означают нехватку памяти, высокий `wa` — ожидание диска.
- «Suppressed messages» — служба писала слишком часто.
- Расхождение времени в журналах проверяют через `timedatectl`.
