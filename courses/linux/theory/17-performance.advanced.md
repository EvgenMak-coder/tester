# Разбор срабатывания OOM killer

```
Out of memory: Killed process 2291 (java) total-vm:9154320kB, anon-rss:7340112kB
```

Запись в журнале ядра называет жертву и её размеры: `total-vm` — адресное пространство, `anon-rss` — занятая физическая память, здесь около 7 ГБ. systemd покажет у службы `status=9/KILL`.

Дальше нужно ответить на главный вопрос: виновата ли жертва.

- **Жертва и есть виновник.** У приложения утечка памяти или завышенные настройки: размер кучи Java, число рабочих процессов, размер кэша базы.
- **Жертва невиновна.** Память съел сосед, а убили самого большого. Выше в журнале ядро печатает таблицу всех процессов с их памятью на момент срабатывания — по ней это видно.

Ядро выбирает жертву по оценке, которую можно сдвинуть. Значение от -1000 до 1000 прибавляется к оценке процесса:

```
echo -1000 > /proc/1234/oom_score_adj
```

`-1000` полностью исключает процесс из кандидатов, `1000` делает его первым. Для служб то же задаёт директива `OOMScoreAdjust=`. Защищать так стоит единицы — например, сервер SSH. Если убивать некого, зависнет вся система.

# Лимиты служб

Служба получает «Too many open files». Администратор выполняет `ulimit -n 65535` в терминале, перезапускает службу — ошибка остаётся.

`ulimit` действует на оболочку и её потомков. Службу же запускает systemd, а не ваш терминал, и она наследует лимиты от него. Файл `/etc/security/limits.conf` тоже не поможет: он применяется при входе пользователя в систему, а службы в систему не входят.

Лимиты службы задаёт её юнит:

```
[Service]
LimitNOFILE=65535
```

Проверить, что лимит действует, можно по самому процессу: `cat /proc/номер/limits`.

# cgroups: жёсткие ограничения

`nice` и `ionice` расставляют приоритеты. Они ничего не ограничивают: процесс с низшим приоритетом займёт весь свободный ресурс. Настоящие потолки ставят через **cgroups** — механизм ядра, который учитывает и ограничивает ресурсы группы процессов.

Каждая служба systemd работает в своей группе:

```
[Service]
CPUQuota=50%
MemoryMax=2G
IOWeight=50
```

- `CPUQuota=50%` — не больше половины одного ядра, даже если остальные простаивают; 200% соответствует двум ядрам;
- `MemoryMax` — потолок памяти; при превышении срабатывает OOM killer внутри группы, не задевая остальную систему;
- `IOWeight` — доля ввода-вывода при конкуренции.

Потребление по группам в реальном времени показывает `systemd-cgtop`. На тех же cgroups построены ограничения ресурсов контейнеров.

# Сводка системных вызовов: strace -c

Полный вывод `strace` для нагруженной программы — тысячи строк в секунду. Ключ `-c` заменяет поток сводной таблицей:

```
strace -c ./import
```

```
% time     seconds  usecs/call     calls    errors syscall
 84.12    3.214500          12    267875           write
  9.31    0.355800          40      8895           fsync
  3.02    0.115400           3     38460      1220 openat
```

Для каждого вызова видно, сколько раз он выполнен, сколько времени занял и сколько раз завершился ошибкой. Здесь программа сделала четверть миллиона мелких записей: её время уходит на переходы в ядро, и объединение записей в крупные блоки ускорит её в разы.

С ключом `-p` та же сводка снимается с работающего процесса: `strace -c -p 1234`, остановка по Ctrl+C.

# Профилирование: perf

`strace` видит только обращения к ядру. Если процесс занимает ядро на 100% и почти не делает системных вызовов, он занят собственными вычислениями, и нужен другой инструмент.

```
sudo perf top
sudo perf record -g -p 1234
sudo perf report
```

`perf` много раз в секунду записывает, какую функцию выполняет процессор. `perf top` показывает самые «горячие» функции по всей системе в реальном времени. `perf record` собирает данные по одному процессу; ключ `-g` добавляет цепочки вызовов, чтобы было видно, кто вызвал горячую функцию. `perf report` показывает, где накопилось больше всего отсчётов.

Правило выбора: высокий `sy` — берите `strace -c`, высокий `us` — `perf`.

# Состояние D

```
  PID STAT CMD
 5120 D    cp /mnt/nfs/big.iso /data/
```

Буква `D` означает непрерываемое ожидание. Процесс находится внутри системного вызова и ждёт устройство: умирающий диск или не отвечающий сервер NFS.

Сигналы ему не доставляются, пока операция не закончится. Поэтому на него не действует даже `kill -9`: сигнал поставлен в очередь и будет обработан, когда ядро вернёт управление.

Такие процессы входят в load average. Высокая нагрузка при свободном процессоре и высоком `wa` означает, что много процессов стоит в состоянии D. Лечить нужно причину ожидания: диск, сеть, сетевое хранилище.

# Время, отнятое гипервизором

```
%Cpu(s): 21.3 us,  4.1 sy,  0.0 ni, 32.0 id,  0.6 wa,  0.0 hi,  0.5 si, 41.5 st
```

`st` (steal) — время, когда виртуальная машина была готова работать, но физический процессор был отдан другим машинам на том же сервере.

Изнутри машины это не исправить. Программы ни при чём, настройки ни при чём: 41% времени процессора у вас попросту нет. Нужно обращаться к хостингу, переезжать на менее загруженный узел или на тариф с выделенными ядрами.

# Утечка памяти

Заподозрить утечку легко, ошибиться ещё легче. Признаки, которые **не** говорят об утечке:

- мало памяти в столбце `free` — она занята кэшем;
- огромный VIRT — это зарезервированное, а не использованное;
- рост памяти в первые минуты после запуска — программа загружает данные и прогревает собственные кэши.

Настоящий признак один: **RES процесса неуклонно растёт при постоянной нагрузке** и не выходит на плато. График выглядит как прямая, ползущая вверх сутками, пока не придёт OOM killer.

Убедиться можно, записывая значение по времени:

```
ps -o rss= -p 1234
```

Подробную раскладку памяти процесса по областям даёт `pmap -x 1234`. Временная мера до исправления программы — потолок `MemoryMax` и автоматический перезапуск.

# Кэш записи

Копирование большого файла на медленную флешку «завершается» за две секунды, а индикатор мигает ещё минуту.

Запись сначала попадает в оперативную память: изменённые страницы называют «грязными». Программа получает ответ «готово» сразу, а ядро переносит данные на устройство в фоне. Это сильно ускоряет работу, но данные, которые ещё не дошли до диска, при отключении питания пропадут.

```
sync
```

`sync` дожидается, пока все грязные данные будут записаны. То же делает размонтирование. Сколько данных ждёт записи, видно в `/proc/meminfo`, в строке `Dirty`.

Программы, которым важна сохранность, например базы данных, сами вызывают `fsync` после каждой важной записи и не полагаются на фоновый перенос. Поэтому они так чувствительны к скорости диска.

# Порядок диагностики

1. `uptime` и `nproc` — есть ли нагрузка и сколько ядер.
2. `top` — строка процессора: `us`, `sy`, `wa` или `st`?
3. `free -h` — что с `available` и подкачкой.
4. `iostat -x 1` — не перегружен ли диск.
5. `dmesg` — нет ли ошибок оборудования и следов OOM killer.
6. Найдя ресурс, ищут процесс: `top`, `iotop`, `ps --sort`.
7. Найдя процесс, смотрят, чем он занят: `strace -c` или `perf`.

# Коротко

- В записи OOM killer смотрят, кто действительно занял память; `oom_score_adj` сдвигает выбор жертвы.
- Лимиты службы задаёт юнит: `LimitNOFILE=`; `ulimit` в терминале на неё не действует.
- cgroups дают жёсткие потолки: `CPUQuota`, `MemoryMax`.
- `strace -c` — сводка системных вызовов, `perf` — профиль функций.
- Состояние D: процесс ждёт ввод-вывод и не принимает сигналы.
- Высокий `st` — процессор забирают другие виртуальные машины.
- Утечка — это неуклонный рост RES при постоянной нагрузке.
- Запись сначала идёт в память; `sync` дожидается переноса на диск.
