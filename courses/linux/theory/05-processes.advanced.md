# Как рождается и умирает процесс

В Linux новый процесс не создаётся с нуля. Он появляется в два шага, и из этой схемы следует почти всё остальное в этом разделе.

1. **fork** — процесс создаёт свою копию. У копии новый PID, но та же программа, те же открытые файлы и то же окружение.
2. **exec** — копия заменяет свою программу другой. PID остаётся прежним.
3. **exit** — программа завершается и оставляет код завершения.
4. **wait** — родитель читает этот код. Только после этого запись о процессе исчезает.

Когда вы набираете `ls`, оболочка делает fork, её копия делает exec программы `ls`, а сама оболочка ждёт в wait.

Отсюда понятно, почему потомок наследует окружение и текущий каталог родителя, но не может их ему изменить. И понятно, откуда берутся зомби: это процесс между шагами 3 и 4.

# Как избавиться от зомби

Зомби уже завершился. Отправлять ему сигналы бесполезно: получать их некому, и `kill -9` ничего не изменит. Запись исчезнет, только когда родитель вызовет wait.

Сначала находят родителя:

```
ps -o pid,ppid,stat,cmd -p 5120
```

Столбец `PPID` — номер родителя. Дальше два пути. Иногда помогает напомнить родителю о потомке сигналом SIGCHLD. Если родитель завис или написан с ошибкой, остаётся завершить его самого: зомби станет сиротой, его усыновит PID 1 и сразу заберёт код завершения.

Один зомби безвреден. Сотни зомби от одного родителя — признак ошибки в его программе, и рано или поздно они займут все свободные номера процессов.

# Каталог /proc

Для каждого процесса ядро показывает каталог `/proc/PID`. Файлов на диске за ним нет: содержимое формируется при чтении. Это главный источник сведений о процессе, когда нет специальных инструментов.

- `cmdline` — командная строка, которой процесс запущен;
- `cwd` — ссылка на его текущий каталог;
- `exe` — ссылка на исполняемый файл;
- `environ` — окружение на момент запуска;
- `status` — состояние, память, владелец;
- `limits` — действующие ограничения;
- `fd/` — открытые файлы, по ссылке на каждый дескриптор.

```
ls -l /proc/1234/fd
tr '\0' '\n' < /proc/1234/environ
```

Первая команда показывает, какие файлы и сокеты держит процесс. Вторая выводит его окружение: записи в `environ` разделены нулевым байтом, и `tr` заменяет его переводом строки.

Через `fd` можно даже спасти удалённый файл, пока процесс его не закрыл: скопировать `/proc/1234/fd/5` в обычный файл.

# Состояния процесса

В столбце `STAT` вывода `ps` стоит буква состояния.

- `R` — выполняется или готов выполняться и ждёт процессор.
- `S` — спит: ждёт события, например ввода или ответа по сети. В этом состоянии большинство процессов большую часть времени.
- `D` — непрерываемое ожидание, обычно ввода-вывода.
- `T` — остановлен сигналом, например после Ctrl+Z.
- `Z` — зомби.

Состояние `D` особенное. Процесс находится внутри ядра и ждёт устройство: медленный диск или не отвечающий сервер NFS. Сигналы ему не доставляются, пока операция не закончится, поэтому на него не действует даже `kill -9`. Лечить приходится причину ожидания.

# Нагрузка без нагрузки

Процессы в состоянии `D` входят в load average наравне с теми, кто ждёт процессор. Отсюда картина, которая сбивает с толку: средняя нагрузка 12 на четырёх ядрах, а процессор почти простаивает.

Подтверждает догадку строка процессора в `top`:

```
%Cpu(s):  3.1 us,  1.2 sy,  0.0 ni, 12.4 id, 83.0 wa
```

`wa` — доля времени, когда процессор простаивал в ожидании ввода-вывода. Высокое `wa` при высокой нагрузке означает, что все стоят в очереди к диску, а не к процессору.

# Сигналы: тонкости

**Два сигнала нельзя ни перехватить, ни проигнорировать:** SIGKILL и SIGSTOP. Их обрабатывает ядро, программа о них даже не узнаёт. Все остальные программа может обработать по-своему. В том числе SIGTSTP, который посылает Ctrl+Z: он похож на SIGSTOP, но это другой сигнал, и перехватить его можно.

**Сигнал 0 ничего не отправляет.** Он только проверяет, существует ли процесс и есть ли у вас право на него влиять:

```
kill -0 4242 && echo "работает"
```

Этим пользуются в скриптах, чтобы узнать, жив ли процесс.

**Сигнал можно послать группе процессов**, указав отрицательный номер: `kill -- -4242`. Два дефиса нужны, чтобы минус не был принят за ключ.

# Защитить уже запущенное задание

`nohup` действует только при запуске. Если долгая команда уже работает, а терминал пора закрывать, её отвязывают от оболочки:

```
disown -h %1
```

Обычный порядок такой: Ctrl+Z приостанавливает программу, `bg` продолжает её в фоне, `disown -h` велит оболочке не пересылать заданию SIGHUP при выходе.

# Почему nice не ограничивает

Значение nice — это вес при дележе процессора, а не потолок. Оно имеет смысл только при конкуренции. Если ядро свободно, процесс с nice 19 получит его целиком и будет показывать 100% в `top`.

Жёсткое ограничение ставят иначе — через cgroups. Для службы systemd это одна строка в unit-файле:

```
CPUQuota=50%
```

С ней служба не получит больше половины одного ядра, даже если остальные простаивают.

У диска свой аналог nice — команда `ionice`: она задаёт очерёдность доступа к вводу-выводу.

# Найти самых прожорливых

`ps` умеет сортировать сам:

```
ps aux --sort=-%mem | head -n 6
ps aux --sort=-%cpu | head -n 6
```

Минус перед именем столбца означает порядок по убыванию. `head -n 6` оставляет заголовок и пять процессов.

# Коротко

- Процесс появляется через fork и exec, а исчезает, когда родитель вызывает wait.
- Зомби нельзя убить; нужно, чтобы код забрал родитель, либо завершить родителя.
- `/proc/PID` показывает командную строку, окружение, каталог и открытые файлы процесса.
- `D` — ожидание ввода-вывода: сигналы не действуют, а load average растёт при свободном процессоре.
- SIGKILL и SIGSTOP перехватить нельзя; `kill -0` только проверяет, жив ли процесс.
- `disown -h` защищает от SIGHUP уже запущенное задание.
- nice — приоритет при конкуренции; жёсткий лимит задают через cgroups.
- `ps aux --sort=-%mem | head` показывает главных потребителей памяти.
